## 목표

**사용자 신호가 뼈대 수정을 트리거하고, 그 수정이 실제 개선이었음을 확인한다.**

> 사용자의 질문은 그 사용자의 부족함이 아니라 콘텐츠의 결함 신고다.

이 마일스톤이 3개월 성공 기준 그 자체다. 로드맵의 나머지는 전부 여기에 도달하기 위한 준비다.

## 완료 기준 (DoD)

3개월 성공 기준과 1:1로 대응한다.

- [ ] **(필수)** 사용자 신호가 집계되어 뼈대 수정을 트리거한 사례가 **1건 이상** 존재한다
- [ ] 수정 이후 해당 챕터의 오답률 · 질문 집중도가 실제로 하락했음을 리포트로 확인할 수 있다
- [ ] 자동 반영이든 수동 반영이든 제안 · 승인 이력이 전부 남는다
- [ ] 수정 전후 신호가 **블록 ID로 이어진다**

## 페이즈

### P5.1 신호 집계 ✅

- [x] Kafka 컨슈머 → 집계 테이블
- [x] **블록 단위** 집계 — 질문 수, 시도 수, 오답률
- [x] 딜리버리 형태를 함께 저장하되 집계 키에는 넣지 않는다

`collective_signal_events` 가 원장이다. PK 를 원본 `signal_id` 로 그대로 써서 재수신을 저장 시점에
막고(멱등), 집계는 별도 카운터 없이 `FILTER` 로 그때그때 구한다 — 카운터를 따로 두지 않으니 원장과
어긋날 수도 없다. 컨슈머(`CollectiveSignalListener`)가 보충 블록과 `PROGRESS`(블록 없음)를 진입
시점에 걸러 원장에는 공용 본문 블록 신호만 남는다.

> 형태별로 집계를 나누면 신호가 형태 수만큼 쪼개져 초기 규모에서 어느 쪽도 임계치를 못 넘는다.
> 주제 통합과 정확히 같은 이유다. 형태는 **수정안의 근거**로만 분해한다(P5.3).

### P5.2 임계치 검사

- [ ] 설정값으로 분리 — 예: 같은 지점 질문 5건, 또는 시도 20회 이상에서 오답률 40% 초과
- [ ] 관리 화면에서 조정 가능
- [ ] **실제 수치 확정**

비율 기반이 아닌 이유는 초기 표본이 작아서다. 소비자가 3명일 때 1명만 물어도 33%가 되어
오작동한다. 상대 이상치 탐지는 비교할 데이터가 쌓인 뒤에 도입한다.

### P5.3 수정안 생성

- [ ] AI가 수정안 + **근거** 생성 — 어떤 질문·오답이 어느 블록에 얼마나 모였는지
- [ ] 근거에 **형태별 분해** 첨부 — "이 지점은 웹에서만 오답률이 높다"
- [ ] 반영 직전 검증 패스로 주장–출처 일치 검사

### P5.4 승인 대기열

- [ ] 수정안 목록 · 상세 · 승인 · 기각
- [ ] 반영 모드 전환 — (a) 승인 후 반영 (b) 자동 반영
- [ ] **자동 반영도 이력을 남긴다** — "자동 승인됨"으로 기록

두 모드는 *반영 시점*만 다르고 감사 추적은 동일하다. AI가 생성한 콘텐츠를 AI가 다시 고치는
구조에서 "언제 무엇이 왜 바뀌었는가"가 **유일한 되돌리기 수단**이다.

### P5.5 반영과 재생성

- [ ] 반영 → 챕터 버전 업 (스냅샷)
- [ ] 캐시는 버전 키라 자동 전환 — 무효화 호출 없음
- [ ] 활성 형태의 파생 자산 재생성 트리거 (M6 이후에는 영상·PPT 포함)
- [ ] 학습 이력이 있는 사용자에게 **"이 챕터는 개선되었습니다"** 배지 + 변경 요약

재방문 자체가 개선 효과를 재는 신호가 된다.

### P5.6 효과 측정 리포트

- [ ] 수정 전후 오답률 비교
- [ ] 수정 전후 질문 집중도 비교
- [ ] 이전 버전은 삭제하지 않는다 — 이 비교가 3개월 성공 기준 2번이다

### P5.7 블록 ID 승계 검증 ★

- [ ] 수정 전후 블록 ID가 실제로 이어지는지 검증
- [ ] ID가 갈리는 케이스 탐지 · 승계 규칙 보완
- [ ] M2 P2.1에서 정한 규칙의 실전 검증

> **이 마일스톤의 진짜 관문이다.** 수정으로 블록 ID가 전부 갈리면 수정 전후 신호를 이어 볼 수
> 없고, P5.6이 성립하지 않는다. 즉 3개월 성공 기준 2번이 깨진다. P5.6보다 먼저 확인해도 좋다.

## 여기서 정해야 할 것

| 항목 | 비고 |
|------|------|
| 임계치의 실제 수치 | 시드 사용자가 수십 명일 때도 루프가 한 바퀴 도는 값 |
| 블록 ID 승계 방식 확정 | M2에서 설계, 여기서 검증 후 확정 |
| 재검증 주기 | 같은 블록이 반복 수정될 때의 쿨다운 |

## 리스크

| 리스크 | 대응 |
|--------|------|
| 사용자가 적어 임계치에 영영 도달하지 못한다 | 시드를 **소수 주제에 집중**(M3 P3.7). 임계치를 낮은 절대치로 시작 |
| 블록 ID가 승계되지 않아 전후 비교가 불가능 | P5.7을 P5.6보다 먼저 돌린다 |
| 수정이 오히려 나빠져도 알 수 없다 | P5.6이 하락을 못 보이면 롤백. 이전 버전 보관이 그 수단 |
| 자동 반영에서 오류가 누적된다 | 초기에는 **승인 후 반영** 모드로 운영. 자동은 신뢰가 쌓인 뒤 |
