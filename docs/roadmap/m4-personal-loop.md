## 페이즈

### P4.1 사용자 레이어 저장 ✅

- [x] 응답 · 퀴즈 결과 · 질문을 **챕터 ID 기준**으로 축적
- [x] 뼈대 버전이 올라가도 레이어가 유지되는지 확인 (실제 PostgreSQL 로)
- [x] 이해도 구간 `UNKNOWN / STRUGGLING / LEARNING / CONFIDENT`
- [x] `GET /api/skeletons/{id}/my-layer` · `GET /api/chapters/{id}/my-layer`

**레이어를 별도 테이블에 쌓지 않는다 — 신호에서 파생한다.** 신호가 이미 `(사용자, 챕터)` 기준으로
축적되고 있으므로 집계 테이블을 나란히 두면 이중 기록이 되고, 둘이 어긋나면 **에러 없이 잘못된 추천**이
나온다. 집계는 SQL 에서 한다(경로 결정이 뼈대 전체의 챕터별 요약을 한 번에 필요로 한다). 규모가 커져
조회가 무거워지면 그때 집계 테이블을 붙이고, 그때도 원천은 신호다.

**챕터 ID 기준이라는 사실이 완료 기준 4번을 만족시킨다.** 신호는 챕터에 붙고 버전은 데이터로만 담기므로,
뼈대가 수정돼 v2 가 되어도 v1 의 기록이 그대로 남는다 — Testcontainers PostgreSQL 로 확인했다.

**모르는 것과 낮은 것을 구분한다.** 시도가 2회 미만이면 `UNKNOWN` 이다. 합치면 처음 온 사용자를 "막힌
사람"으로 취급해 선행 챕터로 되돌리게 되고, 그건 진입 자체를 막는다.

**질문이 시도보다 많으면 막힌 것으로 본다.** 퀴즈를 풀기 전에 여러 번 물었다는 뜻이고, 그때 정답률은
아직 아무것도 말해 주지 않는다. 질문 한 건은 판정을 바꾸지 않는다 — 한 번 묻고 이해한 경우가 흔하다.

**구간과 원자료를 함께 내린다.** 구간만 주면 화면이 "왜 그렇게 판정됐나"를 보여 줄 수 없고, 원자료만
주면 클라이언트가 구간 규칙을 복제해 서버와 어긋난다.

**보지 않은 챕터도 목록에 있다.** 뼈대는 항상 완결 상태이므로 "전체 중 어디까지"의 분모가 있어야 하고,
본 것만 내리면 끝까지 소비된 비율(3개월 성공 기준 3번)을 계산할 수 없다.

**진행률이 숫자임을 도메인이 보장한다.** 집계가 SQL 에서 숫자로 캐스팅하므로 문자열 한 줄이 섞이면 그
사용자의 레이어 조회가 통째로 실패한다 — 저장 시점에 막는 편이 싸다.

### P4.2 경로 개인화 ✅

- [x] 그래프에서 다음에 볼 챕터를 이해도에 맞춰 선택 — `NextChapterChoice`(순수 도메인 규칙)
- [x] 개인 루프는 **동기 읽기** — 이웃은 Neo4j, 이해도는 Postgres에서 곧바로
- [x] `GET /api/chapters/{id}/next` — 순서 있는 후보 + **이유**

**규칙을 도메인에 순수 함수로 뒀다.** 이 규칙이 제품의 핵심 동작이고 저장소와 무관하기 때문이다. 서비스에
두면 "이해도가 다른 두 사용자가 다른 경로를 받는다"(완료 기준 1번)를 확인하려고 그래프와 신호를 함께
세워야 하고, 그러면 그 사실을 값으로 고정할 수 없다.

**순서가 곧 설계다.** ① 막혀 있으면 선행으로 되돌린다(앞으로 밀어도 같은 지점에서 다시 막힌다) →
② 충분히 이해했으면 심화 먼저 → ③ 다음 단계 → ④ 연관 → ⑤ 이미 끝낸 챕터는 맨 뒤(REVIEW).
**선행을 이미 이해했다면 되돌리지 않는다** — 아는 것을 다시 읽는 것은 막힘을 풀지 못한다.

**이유를 함께 내린다.** 순서만 주면 "왜 앞으로 안 가고 뒤로 가나"에 답할 수 없고, 그러면 사용자는 추천을
무시하고 목차처럼 훑는다 — 그 순간 그래프로 둔 이유가 사라진다.

**하나로 좁히지 않는다.** 서버가 하나만 주면 그건 다시 목차다. 첫 번째가 추천이고 나머지는 대안이다.

**1홉만 본다.** 2홉 이상을 후보로 내밀면 "다음"이 아니라 목차가 되고, 지금 갈 수 없는 곳까지 섞인다.

**끝까지 본 챕터는 앞 단계 전부를 건너뛴다.** 단계 안에서만 뒤로 밀면 그 단계의 유일한 후보일 때 여전히
맨 앞에 온다 — 테스트가 그 구현을 잡아냈다.

**추천 엔드포인트를 이웃 조회와 나눴다.** 이웃은 **구조**이고 추천은 **그 사람에게 맞춘 순서**다. 한
응답에 섞으면 캐시할 수 있는 것과 없는 것이 함께 들어간다.

### P4.3 보충 블록 ✅

- [x] 막힌 지점에 추가 설명 · 예시를 **삽입** — `POST /api/chapters/{id}/blocks/{blockId}/supplement`
- [x] 본문 블록은 읽기 전용 — 수정 경로 자체를 만들지 않는다
- [x] 생성 단계는 AI 프로바이더 설정의 `PERSONALIZATION` 을 따르고 **AI 게이트웨이를 지난다**
- [x] `layer_supplement_blocks` (V15). 블록 ID 는 그 행의 PK 다 (`s{pk}`)

**삽입만 가능한 구조를 세 층에서 강제했다.** 테이블에 본문 블록을 가리켜 바꾸는 컬럼이 없고, 도메인
타입(`SupplementBlock`)이 앵커와 새 블록만 들고, 합성 함수가 기존 `Block` 인스턴스를 그대로 옮긴다.
규칙으로 두면 언젠가 깨지므로 구조로 막았다 — 본문이 사용자마다 달라지는 순간 집단 루프가 멈춘다.

**블록 ID 를 저장하지 않고 PK 에서 만든다.** 순번을 계산해 발급하면 지운 뒤 다시 만들 때 지워진 ID 가
되살아나고, 그러면 두 설명의 신호가 한 블록에 섞인다. BIGSERIAL 은 되돌아가지 않으므로 재사용이
구조적으로 불가능하다.

**생성 시점을 정했다 — 요청 시 즉시 생성하고 레이어에 남긴다.** 사전 생성은 아무도 막히지 않은 지점의
설명까지 만들어야 하고 그 비용이 블록 수 × 사용자 수로 늘어난다. 같은 지점을 다시 요청하면 이미 만든
것을 돌려주므로 새로고침이 LLM 호출이 되지 않고, DB 의 UNIQUE 가 그 방어선의 마지막 층이다.

**AI 호출은 게이트웨이를 지난다.** 예산 상한 검사가 그 한 곳에만 있기 때문이다 — 개인화 호출을 직접
벤더에 보내면 뼈대당·일일 상한 밖으로 새는 경로가 하나 생긴다. 뼈대 ID 를 달고 부르므로 이 비용도 그
뼈대의 상한에 들어간다.

**프롬프트가 "본문을 다시 쓰지 마라"고 명시한다.** 모델에게 문단 개선을 시키면 개선된 문단이 돌아오고,
그것을 삽입하면 사용자는 같은 내용을 두 번 읽는다. 그 사용자의 **질문과 오답**을 함께 넣는다 — 무엇이
막혔는지가 없으면 이미 본문에 있는 이야기를 반복하는 설명이 나온다.

**빈 응답은 저장하지 않는다.** 빈 보충 블록을 저장하면 다시 요청해도 "이미 있다"로 판정돼 그 지점이
**영구히 빈칸**이 된다.

> 보충 블록이 본문을 고치기 시작하면 집단 루프가 무너진다. 여러 사람이 각자 다른 텍스트를 봤다면
> "같은 지점에서 틀렸다"를 비교할 수 없고, 그 비교가 이 제품의 핵심 메커니즘이다. 삽입만 가능한
> 구조로 **강제**한다 — 규칙으로 두면 언젠가 깨진다.

### P4.4 퀴즈 난이도 조절 ✅

- [x] 같은 챕터에서 문항 난이도를 사용자별로 조절 — `QuizSelection`(순수 도메인 규칙)
- [x] 난이도가 집단 신호 집계를 오염시키지 않도록 신호에 난이도를 함께 기록
- [x] `QuizDifficulty` 는 블록 **속성**이다 (`EASY / CORE / HARD`)

**문항을 만들지 않고 고른다.** 사용자마다 문항을 새로 생성하면 같은 지점의 오답률을 겹쳐 볼 수 없고
생성 비용이 사용자 수만큼 늘어난다. 문항은 공용이고 **누구에게 보이는지만** 달라진다 — 그래서 난이도가
블록 속성이다.

**`CORE` 는 누구에게나 보인다.** 그래서 이해도를 모르는 사용자도 풀 문항이 있고, 모든 문항이 최소 한
집단에서는 비교 대상이 된다 — 어느 문항도 아무도 보지 않는 상태가 되지 않는다. 난이도가 없거나 모르는
값인 문항도 `CORE` 다: 기존 문항에 난이도를 뒤늦게 붙일 수 있어야 하고, 없는 것을 "쉬움"이나 "어려움"으로
취급하면 그 문항이 일부 사용자에게서 조용히 사라진다.

**막힌 사용자에게 어려운 문항을 내밀지 않는다.** 오답이 쌓여 더 막힌 것으로 판정되고, 그러면 이해도
판정이 자기 자신을 강화하는 고리가 생긴다. 반대로 배우는 중인 사용자에게 쉬운 문항을 얹지도 않는다 —
이해도가 실제보다 높게 나오고 그 값이 다음 챕터 선택을 흔든다.

**설명 본문은 이해도와 무관하게 그대로다.** 개인화가 바꾸는 것은 보충 블록 삽입과 문항 선택 둘뿐이고,
그 사실을 값으로 고정했다.

**신호에 난이도를 기록한다** — 리스크 표 1번의 대응이다. 사용자마다 다른 문항을 보므로 난이도 없이
오답률을 합치면 쉬운 문항을 본 집단과 어려운 문항을 본 집단이 섞여 **집단 신호가 조용히 흐려진다.**
서버가 채점할 때 그 문항의 난이도를 함께 넣으므로 클라이언트가 값을 정할 수 없다. M5 임계치 판정이 이
값으로 보정한다.
