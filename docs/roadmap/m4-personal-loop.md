## 페이즈

### P4.1 사용자 레이어 저장 ✅

- [x] 응답 · 퀴즈 결과 · 질문을 **챕터 ID 기준**으로 축적
- [x] 뼈대 버전이 올라가도 레이어가 유지되는지 확인 (실제 PostgreSQL 로)
- [x] 이해도 구간 `UNKNOWN / STRUGGLING / LEARNING / CONFIDENT`
- [x] `GET /api/skeletons/{id}/my-layer` · `GET /api/chapters/{id}/my-layer`

**레이어를 별도 테이블에 쌓지 않는다 — 신호에서 파생한다.** 신호가 이미 `(사용자, 챕터)` 기준으로
축적되고 있으므로 집계 테이블을 나란히 두면 이중 기록이 되고, 둘이 어긋나면 **에러 없이 잘못된 추천**이
나온다. 집계는 SQL 에서 한다(경로 결정이 뼈대 전체의 챕터별 요약을 한 번에 필요로 한다). 규모가 커져
조회가 무거워지면 그때 집계 테이블을 붙이고, 그때도 원천은 신호다.

**챕터 ID 기준이라는 사실이 완료 기준 4번을 만족시킨다.** 신호는 챕터에 붙고 버전은 데이터로만 담기므로,
뼈대가 수정돼 v2 가 되어도 v1 의 기록이 그대로 남는다 — Testcontainers PostgreSQL 로 확인했다.

**모르는 것과 낮은 것을 구분한다.** 시도가 2회 미만이면 `UNKNOWN` 이다. 합치면 처음 온 사용자를 "막힌
사람"으로 취급해 선행 챕터로 되돌리게 되고, 그건 진입 자체를 막는다.

**질문이 시도보다 많으면 막힌 것으로 본다.** 퀴즈를 풀기 전에 여러 번 물었다는 뜻이고, 그때 정답률은
아직 아무것도 말해 주지 않는다. 질문 한 건은 판정을 바꾸지 않는다 — 한 번 묻고 이해한 경우가 흔하다.

**구간과 원자료를 함께 내린다.** 구간만 주면 화면이 "왜 그렇게 판정됐나"를 보여 줄 수 없고, 원자료만
주면 클라이언트가 구간 규칙을 복제해 서버와 어긋난다.

**보지 않은 챕터도 목록에 있다.** 뼈대는 항상 완결 상태이므로 "전체 중 어디까지"의 분모가 있어야 하고,
본 것만 내리면 끝까지 소비된 비율(3개월 성공 기준 3번)을 계산할 수 없다.

**진행률이 숫자임을 도메인이 보장한다.** 집계가 SQL 에서 숫자로 캐스팅하므로 문자열 한 줄이 섞이면 그
사용자의 레이어 조회가 통째로 실패한다 — 저장 시점에 막는 편이 싸다.

### P4.2 경로 개인화

- [ ] 그래프에서 다음에 볼 챕터를 이해도 · 관심에 맞춰 선택
- [ ] 개인 루프는 **동기 읽기** — Postgres에서 곧바로

### P4.3 보충 블록

- [ ] 막힌 지점에 추가 설명 · 예시를 **삽입**
- [ ] 본문 블록은 읽기 전용 — 수정 경로 자체를 만들지 않는다
- [ ] 생성 단계는 AI 프로바이더 설정의 "개인화 보충 블록"을 따른다

> 보충 블록이 본문을 고치기 시작하면 집단 루프가 무너진다. 여러 사람이 각자 다른 텍스트를 봤다면
> "같은 지점에서 틀렸다"를 비교할 수 없고, 그 비교가 이 제품의 핵심 메커니즘이다. 삽입만 가능한
> 구조로 **강제**한다 — 규칙으로 두면 언젠가 깨진다.

### P4.4 퀴즈 난이도 조절

- [ ] 같은 챕터에서 문항 난이도를 사용자별로 조절
- [ ] 난이도가 집단 신호 집계를 오염시키지 않도록 신호에 난이도를 함께 기록

### P4.5 캐시 경계 정리

- [ ] 공용 블록 문서는 `chapter:{id}:v{version}:{format}` 캐시
- [ ] 개인화된 합성 결과는 캐시 대상이 아님 — 경계를 코드로 분리
