## 목표

**주제가 확정되면 비동기로 전 범위를 생성해 `published` 뼈대를 만든다.**

이 마일스톤이 끝나면 소비할 대상이 생긴다. M3의 신호는 전부 여기서 만든 콘텐츠에 붙는다.

## 완료 기준 (DoD)

- [ ] 주제 1개가 비동기 잡으로 전 챕터 생성되어 `published` 상태가 된다
- [ ] 챕터 하나가 실패하면 N회 재시도 후 운영자 큐로 가고, 뼈대는 `published`로 넘어가지 않는다
- [ ] Postgres에 커밋된 챕터가 outbox를 거쳐 Neo4j에 **빠짐없이** 반영된다 (재시도 안전)
- [ ] 뼈대당 또는 일일 비용 상한을 넘으면 생성이 중단되고 알림이 간다
- [x] 챕터를 수정하면 새 버전이 스냅샷으로 쌓이고 이전 버전이 남는다

> 블록 ID 승계 방식을 M5까지 미루면 그때 전면 수정이 된다. 이 시점에 규칙을 정하고, 실제로

#### 블록 ID 규칙 (확정)

규칙이 만족해야 하는 것은 둘이고, **두 번째가 더 위험하다.**

1. **버전이 올라가도 유지된다** — 수정으로 ID가 전부 갈리면 수정 전후 신호를 이어 볼 수 없다
2. **재사용되지 않는다** — v1의 `b3`가 v5에서 다른 내용이 되면 두 버전의 신호가 한 블록에 섞인다.
   이쪽은 **에러 없이** 잘못된 결론을 만든다

| | 규칙 |
|---|------|
| 형식 | `b{순번}` — 소문자 b + 1 이상의 정수 |
| 발급 | **챕터에 저장된 단조 증가 카운터**(`chapters.block_id_sequence`). 되돌리지 않는다 |
| 승계 | 수정 프롬프트에 기존 문서를 ID와 함께 넣고 "유지되는 블록은 같은 ID를 쓰라"고 지시 |
| 검증 | 돌려받은 ID가 기존 집합에 없거나·형식이 틀리거나·문서 안에서 중복이면 **버리고 새로 발급** |
| 삭제 | 지워진 ID는 비어 있는 채로 남고 다시 쓰이지 않는다 |

**잘못된 ID를 통과시키는 것보다 신호가 새 블록에서 다시 시작하는 편이 낫다.** 전자는 다른 블록의
신호를 오염시키고, 후자는 그 블록의 신호만 끊는다.

카운터를 문서에서 계산하지 않고 챕터에 저장하는 이유가 규칙의 핵심이다. 문서의 최대 순번으로
다음 값을 정하면 블록을 지웠다가 추가할 때 지워진 ID가 되살아난다. (카운터가 뒤처져 있을 때는
문서의 최대 순번으로 따라잡아 **재사용만은** 막는다.)

#### 그 밖에 정한 것

**`ProposedBlock` 을 따로 뒀다.** 모델은 ID를 빠뜨리거나 `"new"` 같은 값을 넣는다. 제안을 그대로
`Block`으로 만들려 하면 그 순간 예외가 나고 승계 규칙이 개입할 자리가 없어진다.

**본문 기록 경로가 하나다.** 생성(③)과 수정(집단 루프·검수·검증 패스)이 같은
`RecordChapterBodyUseCase`를 지난다. 나누면 ID 승계와 버전 증가 규칙이 두 곳에 복제되고, 한쪽만
고치는 순간 조용히 어긋난다.

**`current_version = 0` 이 "본문 없음"이다.** 별도 플래그를 두지 않았고, 그래서 published 전환
조건("전 챕터 완료")이 한 쿼리로 판정된다.

**저장 형식을 도메인 레코드와 분리했다.** 블록 문서 jsonb는 별도 DTO를 지난다 — 도메인 레코드를
직접 직렬화하면 필드 이름을 바꾸는 리팩터링이 이미 저장된 문서를 읽을 수 없게 만들고, 그 실패는
배포 후에야 드러난다.

그 위에서 각 단계가 자기 리스너를 등록한다.

#### 토픽 네이밍 (확정)

`{집합체}.{단계}.{이벤트}` — 소문자, 점 구분. 집합체를 앞에 두면 토픽 목록이 알파벳순으로 정렬될 때
같은 집합체가 모인다. 이벤트를 과거분사로 두는 이유는 토픽이 "일어난 일"을 담기 때문이다 —
명령형(`create-body`)은 컨슈머가 하나뿐이라는 가정을 이름에 박는다.

이름은 코드 상수가 아니라 설정값이고 `nextchapter.kafka.prefix`를 앞에 붙일 수 있다. 개발·스테이징이
한 클러스터를 쓰면 토픽이 섞여 **한쪽의 재처리가 다른 쪽 데이터를 만든다.**

#### 파티션 전략 (확정)

| 토픽 | 키 | 파티션 | 이유 |
|------|-----|--------|------|
| `skeleton.graph.requested` | 뼈대 ID | 3 | 뼈대당 1건. 동시 생성 뼈대 수가 병렬도다 |
| `skeleton.outline.requested` | 뼈대 ID | 3 | 같음 |
| `skeleton.body.requested` | **챕터 ID** | 12 | 챕터당 1건. 여기가 실제 병렬 구간이다 |

**본문 토픽의 키가 챕터 ID인 것이 이 표의 핵심이다.** 뼈대 ID를 키로 쓰면 한 뼈대의 챕터가 전부 같은
파티션에 몰려 병렬도가 1이 된다 — 챕터 30개짜리 뼈대의 본문 생성이 순차로 돌고, 파티션을 늘려도 아무
효과가 없다. 그 실패는 에러 없이 "그냥 느린 것"으로 보인다.

키를 아예 비우면 라운드로빈으로 흩어져 병렬도는 나오지만 같은 챕터의 재시도가 다른 파티션에 갈 수
있다. 챕터 ID를 키로 두면 병렬도와 챕터별 순서를 동시에 얻는다.

**토픽을 코드로 선언한다** (`NewTopic` 빈). 브로커 자동 생성에 맡기면 파티션이 브로커 기본값(보통 1)이
되고, 본문 생성이 순차로 돌면서도 아무 에러가 나지 않는다.

#### 그 밖에 정한 것

**페이로드는 문자열 JSON이고 타입 헤더를 쓰지 않는다.** Spring Kafka의 타입 헤더에는 Java 클래스
이름이 박혀서, 클래스를 옮기는 것만으로 토픽에 쌓인 옛 메시지가 죽는다. 도메인 레코드를 직접
직렬화하지 않는 이유도 같다 — 필드 이름을 바꾸는 리팩터링이 이미 쌓인 메시지를 읽을 수 없게 만든다.

**상태 전이와 다음 이벤트 발행이 한 곳을 지난다.** 나뉘면 파이프라인이 조용히 멈춘다 — 상태만 올라가면
아무도 다음 단계를 시작하지 않고, 이벤트만 나가면 진행률이 거짓이 된다.

**전이는 한 칸씩 앞으로만 간다.** 건너뛰면 개요 없이 본문을 쓰거나 본문 없이 자산을 만들게 되고, 그
실패는 생성이 끝난 뒤에야 드러난다. Kafka는 at-least-once이므로 같은 완료 메시지를 두 번 받는 것은
정상이고, 그때는 전이를 건너뛴다.

**`PUBLISHED`는 되돌아가지 않는다.** 챕터 수정 후 자산 재생성은 자산마다 자기 버전으로 추적되고 그동안
준비된 것 중 최신본이 계속 서빙된다. 상태를 되돌리면 "재생성 중에는 형태를 잠근다"가 되어, 개선이
잦을수록 서비스가 나빠지는 역전이 생긴다.

**진행률의 퍼센트는 어림값이고, 챕터 수를 함께 내린다.** 실제 소요시간은 ④가 지배하므로 퍼센트만
보여주면 "80%에서 한 시간"이 버그처럼 보인다. 실패는 퍼센트를 0으로 둔다 — 숫자를 남기면 멈춘 것과
느린 것이 구분되지 않는다.

**개요 이후 챕터가 0개면 실패로 처리한다.** 그대로 두면 완료 판정이 즉시 참이 되어 빈 뼈대가
`published`로 간다. 부분 공개보다 나쁘다.

### P2.6 Transactional Outbox → Neo4j

- [ ] Postgres 트랜잭션 안에서 본문·버전과 outbox를 **같은 커밋**으로
- [ ] 퍼블리셔 → Kafka
- [ ] Neo4j 어댑터가 **멱등** 소비 (멱등 키 = 챕터 ID + 버전)

분산 트랜잭션이 없으므로 순차 쓰기 + 보상은 프로세스가 죽는 구간에서 불일치를 남긴다.
