## 목표

**주제가 확정되면 비동기로 전 범위를 생성해 `published` 뼈대를 만든다.**

이 마일스톤이 끝나면 소비할 대상이 생긴다. M3의 신호는 전부 여기서 만든 콘텐츠에 붙는다.

## 완료 기준 (DoD)

- [ ] 주제 1개가 비동기 잡으로 전 챕터 생성되어 `published` 상태가 된다
- [ ] 챕터 하나가 실패하면 N회 재시도 후 운영자 큐로 가고, 뼈대는 `published`로 넘어가지 않는다
- [x] Postgres에 커밋된 챕터가 outbox를 거쳐 Neo4j에 **빠짐없이** 반영된다 (재시도 안전)
- [ ] 뼈대당 또는 일일 비용 상한을 넘으면 생성이 중단되고 알림이 간다
- [x] 챕터를 수정하면 새 버전이 스냅샷으로 쌓이고 이전 버전이 남는다

#### 블록 ID 규칙 (확정)

규칙이 만족해야 하는 것은 둘이고, **두 번째가 더 위험하다.**

1. **버전이 올라가도 유지된다** — 수정으로 ID가 전부 갈리면 수정 전후 신호를 이어 볼 수 없다
2. **재사용되지 않는다** — v1의 `b3`가 v5에서 다른 내용이 되면 두 버전의 신호가 한 블록에 섞인다.
   이쪽은 **에러 없이** 잘못된 결론을 만든다

| | 규칙 |
|---|------|
| 형식 | `b{순번}` — 소문자 b + 1 이상의 정수 |
| 발급 | **챕터에 저장된 단조 증가 카운터**(`chapters.block_id_sequence`). 되돌리지 않는다 |
| 승계 | 수정 프롬프트에 기존 문서를 ID와 함께 넣고 "유지되는 블록은 같은 ID를 쓰라"고 지시 |
| 검증 | 돌려받은 ID가 기존 집합에 없거나·형식이 틀리거나·문서 안에서 중복이면 **버리고 새로 발급** |
| 삭제 | 지워진 ID는 비어 있는 채로 남고 다시 쓰이지 않는다 |

**잘못된 ID를 통과시키는 것보다 신호가 새 블록에서 다시 시작하는 편이 낫다.** 전자는 다른 블록의
신호를 오염시키고, 후자는 그 블록의 신호만 끊는다.

카운터를 문서에서 계산하지 않고 챕터에 저장하는 이유가 규칙의 핵심이다. 문서의 최대 순번으로
다음 값을 정하면 블록을 지웠다가 추가할 때 지워진 ID가 되살아난다. (카운터가 뒤처져 있을 때는
문서의 최대 순번으로 따라잡아 **재사용만은** 막는다.)

#### 그 밖에 정한 것

**`ProposedBlock` 을 따로 뒀다.** 모델은 ID를 빠뜨리거나 `"new"` 같은 값을 넣는다. 제안을 그대로
`Block`으로 만들려 하면 그 순간 예외가 나고 승계 규칙이 개입할 자리가 없어진다.

**본문 기록 경로가 하나다.** 생성(③)과 수정(집단 루프·검수·검증 패스)이 같은
`RecordChapterBodyUseCase`를 지난다. 나누면 ID 승계와 버전 증가 규칙이 두 곳에 복제되고, 한쪽만
고치는 순간 조용히 어긋난다.

**`current_version = 0` 이 "본문 없음"이다.** 별도 플래그를 두지 않았고, 그래서 published 전환
조건("전 챕터 완료")이 한 쿼리로 판정된다.

**저장 형식을 도메인 레코드와 분리했다.** 블록 문서 jsonb는 별도 DTO를 지난다 — 도메인 레코드를
직접 직렬화하면 필드 이름을 바꾸는 리팩터링이 이미 저장된 문서를 읽을 수 없게 만들고, 그 실패는
배포 후에야 드러난다.

그 위에서 각 단계가 자기 리스너를 등록한다.

#### 토픽 네이밍 (확정)

`{집합체}.{단계}.{이벤트}` — 소문자, 점 구분. 집합체를 앞에 두면 토픽 목록이 알파벳순으로 정렬될 때
같은 집합체가 모인다. 이벤트를 과거분사로 두는 이유는 토픽이 "일어난 일"을 담기 때문이다 —
명령형(`create-body`)은 컨슈머가 하나뿐이라는 가정을 이름에 박는다.

이름은 코드 상수가 아니라 설정값이고 `nextchapter.kafka.prefix`를 앞에 붙일 수 있다. 개발·스테이징이
한 클러스터를 쓰면 토픽이 섞여 **한쪽의 재처리가 다른 쪽 데이터를 만든다.**

#### 파티션 전략 (확정)

| 토픽 | 키 | 파티션 | 이유 |
|------|-----|--------|------|
| `skeleton.graph.requested` | 뼈대 ID | 3 | 뼈대당 1건. 동시 생성 뼈대 수가 병렬도다 |
| `skeleton.outline.requested` | 뼈대 ID | 3 | 같음 |
| `skeleton.body.requested` | **챕터 ID** | 12 | 챕터당 1건. 여기가 실제 병렬 구간이다 |

**본문 토픽의 키가 챕터 ID인 것이 이 표의 핵심이다.** 뼈대 ID를 키로 쓰면 한 뼈대의 챕터가 전부 같은
파티션에 몰려 병렬도가 1이 된다 — 챕터 30개짜리 뼈대의 본문 생성이 순차로 돌고, 파티션을 늘려도 아무
효과가 없다. 그 실패는 에러 없이 "그냥 느린 것"으로 보인다.

키를 아예 비우면 라운드로빈으로 흩어져 병렬도는 나오지만 같은 챕터의 재시도가 다른 파티션에 갈 수
있다. 챕터 ID를 키로 두면 병렬도와 챕터별 순서를 동시에 얻는다.

**토픽을 코드로 선언한다** (`NewTopic` 빈). 브로커 자동 생성에 맡기면 파티션이 브로커 기본값(보통 1)이
되고, 본문 생성이 순차로 돌면서도 아무 에러가 나지 않는다.

#### 그 밖에 정한 것

**페이로드는 문자열 JSON이고 타입 헤더를 쓰지 않는다.** Spring Kafka의 타입 헤더에는 Java 클래스
이름이 박혀서, 클래스를 옮기는 것만으로 토픽에 쌓인 옛 메시지가 죽는다. 도메인 레코드를 직접
직렬화하지 않는 이유도 같다 — 필드 이름을 바꾸는 리팩터링이 이미 쌓인 메시지를 읽을 수 없게 만든다.

**상태 전이와 다음 이벤트 발행이 한 곳을 지난다.** 나뉘면 파이프라인이 조용히 멈춘다 — 상태만 올라가면
아무도 다음 단계를 시작하지 않고, 이벤트만 나가면 진행률이 거짓이 된다.

**전이는 한 칸씩 앞으로만 간다.** 건너뛰면 개요 없이 본문을 쓰거나 본문 없이 자산을 만들게 되고, 그
실패는 생성이 끝난 뒤에야 드러난다. Kafka는 at-least-once이므로 같은 완료 메시지를 두 번 받는 것은
정상이고, 그때는 전이를 건너뛴다.

**`PUBLISHED`는 되돌아가지 않는다.** 챕터 수정 후 자산 재생성은 자산마다 자기 버전으로 추적되고 그동안
준비된 것 중 최신본이 계속 서빙된다. 상태를 되돌리면 "재생성 중에는 형태를 잠근다"가 되어, 개선이
잦을수록 서비스가 나빠지는 역전이 생긴다.

**진행률의 퍼센트는 어림값이고, 챕터 수를 함께 내린다.** 실제 소요시간은 ④가 지배하므로 퍼센트만
보여주면 "80%에서 한 시간"이 버그처럼 보인다. 실패는 퍼센트를 0으로 둔다 — 숫자를 남기면 멈춘 것과
느린 것이 구분되지 않는다.

**개요 이후 챕터가 0개면 실패로 처리한다.** 그대로 두면 완료 판정이 즉시 참이 되어 빈 뼈대가
`published`로 간다. 부분 공개보다 나쁘다.

#### 관계 타입 (확정)

| 타입 | 뜻 | 순환 |
|------|-----|------|
| `PREREQUISITE` | A를 이해해야 B를 이해할 수 있다 (단단한 의존) | **금지** |
| `RELATED` | 서로 도움이 되지만 순서는 없다 | 허용 |
| `DEEPENS` | B가 A의 심화다 | 허용 |

**"다음 챕터" 타입을 두지 않았다.** 선형 다음을 간선으로 표현하면 그건 목차이고, 챕터를 그래프로 둔
이유가 사라진다. 순서가 필요한 곳에서는 선행 관계와 정렬 순서에서 나오게 한다 — 그러면 "선행만 채우면
어느 순서로도 갈 수 있다"가 표현된다.

**선행 관계의 순환만 금지한다.** 순환이 있으면 어느 챕터도 선행 조건을 만족시킬 수 없어 진입점이
사라지고, 그 실패는 조회 시점에 예외가 아니라 **"추천할 챕터가 없음"**으로 나타난다. `RELATED`와
`DEEPENS`는 순서를 주장하지 않으므로 순환이 문제가 되지 않는다.

#### 생성 시점에 막는 것

잘못된 그래프는 저장에 성공하고 소비 시점에 드러나는데, 그때는 본문·자산 생성비가 다 든 뒤다.
그래서 저장 전에 거절한다.

- 챕터 키 중복 / 없는 챕터를 가리키는 관계(끊어진 간선) / 자기 참조
- 선행 관계의 순환
- 챕터 수 하한 4, 상한 40 — 적으면 주제를 덮지 못하고, 많으면 생성비가 뼈대 하나에 몰리면서
  **챕터당 신호가 얇아져** 집단 루프가 임계치를 넘기 어려워진다

중복 간선과 자기 참조는 DB 제약으로도 막는다. 애플리케이션 검증을 지나온 뒤에도 동시 요청이나 재생성
경로로 들어올 수 있고, 들어오면 경로 결정의 가중치를 왜곡하면서 에러를 내지 않는다.

#### 재생성은 덮어쓰기다

**관계는 먼저 지우고 다시 넣는다.** 남겨 두면 옛 간선이 새 그래프에 섞여 순환이 생길 수 있고, 그 순환은
생성 시점 검증을 이미 지나온 뒤라 걸리지 않는다.

**챕터는 키로 매칭해 ID를 유지한다.** 지우고 다시 만들면 챕터 ID가 갈리는데, 사용자 레이어와 집단 신호가
챕터 ID 기준으로 붙어 있으므로 그 순간 학습 기록과 신호가 끊긴다. 재생성이 그것을 지울 수는 없다.

#### 파싱 실패를 흘려보내지 않는다

주제 매핑(P1.5)에서는 파싱 실패를 "매칭 실패"로 흘려보냈다 — 사용자가 후보 제시 경로로 갈 수 있었기
때문이다. 그래프 생성에는 그런 대안 경로가 없다. 조용히 빈 그래프를 만들면 챕터 0개짜리 뼈대가 다음
단계로 넘어가고, 완료 판정이 즉시 참이 되어 빈 뼈대가 `published`로 간다.

프롬프트는 **선형 목차를 금지한다고 명시한다.** 지시하지 않으면 모델은 거의 항상 1장·2장·3장 형태를
내놓는다.

겹친다는 것을 알면 그 챕터의 본문 생성비와 파생 자산비가 모두 버려진다.

#### 소견은 본문 생성을 막지 않는다

겹침·누락 판정은 어림이고, **오탐 하나가 파이프라인을 세우면 사전 생성의 이점이 사라진다.** 소견은
기록으로 남겨 운영자 검수가 보게 한다.

막는 것은 하나뿐이다 — **개요가 없는 챕터.** 그건 어림이 아니라 사실이고(본문을 쓸 재료가 없다), 그대로
두면 빈 본문이 생성되어 생성비만 쓴다. 그래서 응답이 **모든 챕터를 정확히 한 번 덮는지**를 검증한다.
빠진 챕터는 재료가 없다는 뜻이고, 중복된 챕터는 어느 개요가 진짜인지 알 수 없다는 뜻이다.

#### 개요와 소견을 한 응답으로 받는다

모델이 전 챕터를 한 번에 보므로 겹침을 만들지 않으면서 동시에 남은 겹침을 보고할 수 있고, 호출이 두
번에서 한 번으로 줄어든다. 개요를 먼저 만든 뒤 별도 호출로 검사하면 같은 정보를 두 번 보낸다.

**프롬프트에 "겹치면 보고하라"를 넣는다.** 겹침을 만들지 말라고만 하면 모델은 겹침을 *숨긴다* — 지시를
지킨 것처럼 보이는 응답을 만드는 쪽이 쉽다. 보고 항목이 응답 형식에 있어야 겹침이 드러나고, 그것이 이
단계의 존재 이유다.

#### 그 밖에

**개요를 `chapters` 컬럼이 아니라 별도 테이블에 뒀다.** 챕터 목록·그래프 조회는 개요를 필요로 하지 않고
(트리 조회는 자주 일어난다), 개요를 필요로 하는 것은 본문 생성과 검수뿐이다.

**재생성은 옛 소견을 지운다.** 이미 고친 겹침이 검수 화면에 남아 있으면 판단을 흐린다.

### P2.5 ③ 본문 생성 ✅

- [x] 챕터 수만큼 메시지 발행 (파티션으로 병렬도 조절) — P2.2·P2.4에서 이미 붙었다
- [x] 블록 문서 생성 (`skeleton.body.requested` 컨슈머)
- [x] 챕터별 **독립 재시도**
- [x] 핵심 주장에 출처 근거 생성 — 출처 없는 본문은 실패로 다룬다

#### 출처는 주장을 하는 블록의 속성이다

별도 블록 타입도, 별도 테이블도 아니다. 검증 패스가 **"주장–출처 일치"**를 검사하기 때문이다 — 둘이
떨어져 있으면 어느 주장에 어느 출처가 붙는지를 다시 추정해야 하고, 그 추정이 틀리면 검증이 통과했다는
사실 자체가 무의미해진다.

**출처가 하나도 없는 본문은 실패로 다룬다.** 검증 패스가 검사할 대상이 없다는 뜻이고, 그 상태는 "검증을
통과했다"와 구분되지 않는다. 재시도 비용이, 나중에 검증할 수 없는 콘텐츠를 안고 가는 비용보다 싸다.

프롬프트는 출처를 **핵심 주장에만** 달라고 한다. 전부에 달게 하면 모델이 형식을 채우려고 아무 문서나
붙이고, 그 출처는 검증을 통과하지 못하면서 검증 비용만 늘린다. URL이 확실하지 않으면 빼라고 지시한다.

#### 중복 메시지가 v2를 만들지 않는다

Kafka는 at-least-once이므로 같은 본문 생성 메시지를 두 번 받는 것이 정상이다. 그때 그냥 생성하면 v2가
쌓이는데, 그건 **수정이 아닌 중복**이고 이력에 "왜 바뀌었는지 설명할 수 없는 버전"을 남긴다. 이미 본문이
있으면 건너뛰고, 수정은 M5의 명시적 경로로만 들어온다.

건너뛴 경우에도 **완료 보고는 한다.** 그 챕터는 끝난 상태이고, 보고하지 않으면 마지막 챕터가 중복
메시지였을 때 파이프라인이 영원히 대기한다.

#### 실패가 챕터 단위로 격리된다

메시지 키가 챕터 ID이므로 실패한 챕터의 메시지만 재시도되고, 같은 뼈대의 다른 챕터는 계속 진행된다.
뼈대 단위로 묶었다면 챕터 하나의 실패가 전부를 되돌린다.

#### 블록 하나가 챕터를 버리게 하지 않는다

알 수 없는 타입이나 필수 항목이 빠진 블록(정답 없는 퀴즈 등)은 **파싱 시점에** 건너뛴다. 남은 블록으로도
본문은 성립한다. 전부 건너뛰어 비게 되면 그때 실패로 올린다.

검증을 파싱 시점에 두는 것이 중요하다. 기록 시점까지 살려 보내면 잘못된 블록 하나가 챕터 전체를
실패시킨다.

#### 프롬프트가 나르는 문맥

개요 항목 + **선행 챕터 제목**(이미 다뤄진 것을 다시 설명하지 않게) + **다른 챕터 제목**(경계를 알려
주지 않으면 한 챕터가 다른 챕터의 범위를 먹는다). `narration`과 `quiz`를 최소 하나씩 요구한다 — 전자는
영상 렌더링의 유일한 원천이고, 후자의 오답률이 집단 루프의 핵심 신호다.

### P2.6 Transactional Outbox → Neo4j ✅

- [x] Postgres 트랜잭션 안에서 본문·버전과 outbox를 **같은 커밋**으로 (`V9__outbox.sql`)
- [x] 퍼블리셔 → Kafka (`FOR UPDATE SKIP LOCKED` + 주기 폴링)
- [x] Neo4j 어댑터가 **멱등** 소비 (멱등 키 = 챕터 ID + 버전)
- [x] Neo4j에는 챕터 ID · 키 · 제목 · 버전 · 관계만 (얇은 그래프)

분산 트랜잭션이 없으므로 순차 쓰기 + 보상은 프로세스가 죽는 구간에서 불일치를 남긴다.

#### 같은 커밋을 코드로 강제했다

`append` 에 `Propagation.MANDATORY` 를 걸었다. 트랜잭션 없이 호출되면 outbox 행이 본문과 다른 커밋에
들어가 두 단계 쓰기가 되는데, **그 상태는 정상 동작처럼 보이고 프로세스가 사이에서 죽을 때만 드러난다.**
MANDATORY 는 그 호출을 즉시 예외로 만든다.

#### 파티션 키가 본문 토픽과 반대다

| 토픽 | 키 | 이유 |
|------|-----|------|
| `skeleton.body.requested` | 챕터 ID | 병렬도. 챕터별로 흩어져야 한다 |
| `chapter.outbox.persisted` | **뼈대 ID** | 순서. 간선이 노드보다 먼저 오면 유령 노드가 생긴다 |

Neo4j 반영은 값싸서 순서를 위해 병렬도를 포기할 수 있다. 반대로 본문 생성은 비싸서 병렬도를 위해 순서를
포기한다(챕터 간 순서는 필요 없다). **같은 시스템에서 정반대 선택을 하는 이유가 작업의 성질이다.**

#### 멱등성은 두 겹이다

- **노드**: 버전이 **더 클 때만** 덮어쓴다. 옛 오프셋에서 재생하면 지난 버전 이벤트가 다시 오는데, 무조건
  덮어쓰면 그래프가 과거로 되돌아가고 **그 되돌림은 에러 없이 일어난다**
- **관계**: 전량 교체다. 그 자체로 멱등이고, 재생성 때 옛 간선이 남아 순환이 생기는 것도 막는다

간선의 양 끝 노드를 `MERGE` 로 만든다. 정상 경로에서는 노드가 먼저 오지만 임의 오프셋 재생에서는 어긋날 수
있고, 그때 **유령 간선이 남는 것보다 속성 없는 노드가 생기는 편이 낫다** — 뒤이어 오는 노드 이벤트가 속성을
채운다.

`Chapter.chapterId` 유일 제약을 만든다. 없으면 `MERGE` 가 동시 실행에서 같은 chapterId 노드를 두 개 만들 수
있고, 그러면 탐색이 챕터를 두 번 세거나 간선이 둘로 갈린다 — 어느 쪽도 에러가 아니다.

#### 발행 실패는 표시하지 않는다

발행과 발행 표시를 같은 트랜잭션에 둔다. 표시가 커밋되지 않으면 다음 폴링이 같은 이벤트를 다시 집어 가는데,
그게 옳은 방향이다 — Neo4j 반영이 멱등이므로 **중복 발행은 안전하고 누락은 아니다.** 반대로 표시를 먼저
커밋하고 발행하면 발행 실패가 곧 유실이 된다.

`FOR UPDATE SKIP LOCKED` 를 쓴다. 잠그지 않으면 인스턴스 두 개가 같은 이벤트를 발행하고, 잠그되 건너뛰지
않으면 한쪽이 다른 쪽을 기다려 처리량이 1로 떨어진다.

#### 폴링을 쓰는 이유

커밋 후 훅으로 즉시 발행하면 지연은 줄지만, 프로세스가 커밋 직후 죽으면 그 이벤트를 다시 집어 갈 사람이
없다. 폴링은 그 경우에도 다음 주기에 반드시 집어 간다 — **지연을 대가로 유실 없음을 얻는다.**

`fixedDelay` 를 쓰는 이유는 한 주기가 길어졌을 때 다음 주기가 겹쳐 돌지 않게 하기 위해서다. `fixedRate` 는
밀린 만큼 몰아서 실행해 Neo4j 쓰기가 한꺼번에 몰린다.

#### 관계를 `RELATES` + `type` 속성으로 뒀다

네이티브 관계 타입이 탐색에는 더 좋지만, 타입이 늘어날 때(M4 개인화가 더 필요로 할 수 있다) Cypher를 고쳐야
한다. 그리고 나중에 성능이 네이티브 타입을 요구하면 **파생 저장소이므로 통째 재구축으로 옮길 수 있다** —
원천이라면 못 할 선택이다.

| 본문 생성 멱등성 | 이미 본문이 있으면 건너뛴다. 건너뛰어도 완료 보고는 한다 |

| 본문 기록 경로 | 생성과 수정이 같은 유스케이스를 지난다 |
