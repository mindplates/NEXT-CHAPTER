## 목표

**운영자가 서비스를 실제로 굴릴 수 있다.**

앞선 마일스톤에서 기능별로 흩어져 만들어진 운영자 화면을 하나의 콘솔로 모으고, 서비스를
지속시키는 데 필요한 나머지를 채운다.

## 완료 기준 (DoD)

- [ ] 운영자가 카탈로그 · 콘텐츠 · 개선 루프 · AI 설정 · 비용을 한 콘솔에서 관리한다
- [ ] 초기 카탈로그가 도메인 1~2개 · 분야 5~10개 · 주제 30~50개로 채워져 있다
- [ ] Neo4j를 통째로 재구축해도 서비스가 복구된다
- [ ] 핵심 사용자 플로우가 E2E로 검증된다

## 페이즈

### P7.1 관리자 콘솔 통합

| 영역 | 내용 | 원래 만들어진 곳 |
|------|------|------------------|
| 카탈로그 | 도메인 · 분야 · 주제 관리, 미매핑 입력 검토 | M1 |
| 콘텐츠 | 뼈대 사전 생성, 검수, 수동 개선 | M2 |
| 개선 루프 | 승인 대기열, 자동/수동 모드, 임계치 설정 | M5 |
| AI 설정 | 단계별 벤더 · 모델, API 키 | M1 |
| 비용 | 뼈대당 · 일일 예산 상한 | M2 |

- [ ] 위 5개 영역을 하나의 콘솔로 통합
- [ ] 운영자 경로를 사용자 경로와 분리 유지

> 이 콘솔은 "B2B 요구사항은 범위에 없다"는 원칙과 무관하다. 조직 분리 · 학습 배정 · 관리자
> 리포팅이 아니라, 공개 서비스를 운영하기 위한 **운영자 도구**다.

### P7.2 초기 카탈로그 시드

- [ ] 도메인 1~2개 · 분야 5~10개 · **주제 30~50개**
- [ ] 사전 생성 비용을 뼈대당 상한 안에서 관리
- [ ] M3 P3.7의 소수 시드에서 확대

**소수 도메인을 깊게** 채운다. 넓고 얕게 펴면 뼈대당 사용자가 1~2명씩 붙어 집단 루프가 임계치를
못 넘는다. 커버리지보다 **한 뼈대에 신호를 모으는 것**이 우선이다.

### P7.3 생성 정확성 검증

- [ ] 검증 패스 — 신규 생성 직후, 뼈대 수정 반영 직전
- [ ] 주장–출처 일치 검사
- [ ] 사용자 오류 신고 → 검증 패스 트리거
- [ ] **적용 범위 확정** — 전 챕터 vs 샘플링

범위는 M2에서 실측한 뼈대당 생성 단가를 보고 정한다.

### P7.4 Neo4j 재구축 절차

- [ ] Neo4j는 파생 저장소이므로 **통째 재생성이 가능해야 한다**
- [ ] 재구축 방식 확정 — outbox 재생 vs Postgres 전량 스캔
- [ ] 실제로 한 번 돌려 복구 시간 측정

### P7.5 관측성

- [ ] 잡 상태 · 실패 큐 대시보드
- [ ] 비용 사용량 (뼈대당 · 일일)
- [ ] 신호량 · 임계치 도달 현황
- [ ] 자산 생성 지연 현황 (형태별)

### P7.6 배포와 운영 형태

- [ ] Kafka 운영 형태 확정 — 자체 운영 vs 매니지드
- [ ] Neo4j 운영 형태 확정
- [ ] 오브젝트 스토리지 운영 형태 확정 (M6에서 결정된 수단 기준)
- [ ] 배포 파이프라인

운영 대상이 5개다. MVP 단계 인프라로 작지 않은 규모라는 점을 감안해 매니지드 비중을 정한다.

### P7.7 E2E

- [ ] Playwright — 핵심 사용자 플로우
- [ ] 주제 입력 → 매핑 확인 → 생성 완료 알림 → 소비 → 퀴즈 → 신호 기록
- [ ] 개선 반영 후 "개선되었습니다" 배지 노출
