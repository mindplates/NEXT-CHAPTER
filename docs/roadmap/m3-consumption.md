## 목표

**사용자가 실제로 소비하고, 여기서부터 신호가 발생한다.**

로드맵 전체에서 가장 중요한 전환점이다. M2까지는 만드는 이야기였고 M3부터는 **데이터가 쌓인다.**
M4·M5·M6가 전부 여기서 나오는 신호와 콘텐츠에 의존한다.

## 완료 기준 (DoD)

- [ ] 소셜 로그인 → 주제 진입 → 그래프 탐색 → 챕터 소비까지 끊김 없이 동작한다
- [ ] 퀴즈 응답 · 질문 · 오류 신고가 **블록 ID와 딜리버리 형태를 달고** 신호로 기록된다
- [ ] 같은 챕터 재조회가 캐시에서 나오고, 뼈대가 수정되면 무효화 호출 없이 새 버전이 나온다
- [ ] 시드 주제로 실제 학습이 가능하다

## 페이즈

### P3.1 사용자 인증 ✅

- [x] OAuth2 소셜 로그인 → JWT — **Google · Kakao**, 인가 코드 교환은 서버가 한다
- [x] 관리자 경로(M1 P1.2)와 분리된 채로 공존 — 필터 체인 두 개, 역할로 구분(`USER` / `ADMIN`)
- [x] `users` 테이블 (V13). 정체성은 `(제공자, 제공자 식별자)`, 비밀번호 컬럼 없음
- [x] `GET /api/auth/providers` · `POST /api/auth/social/{provider}` · `GET /api/auth/me`

**인가 코드를 서버가 교환한다.** 클라이언트가 제공자 토큰을 직접 받아 넘기면 서버는 그 토큰이 우리
앱을 위해 발급된 것인지 확인할 방법이 없고, 클라이언트가 웹·모바일·태블릿으로 늘어날 때마다 제공자
SDK와 시크릿 취급 규칙이 하나씩 생긴다.

**정체성은 이메일이 아니다.** 제공자 쪽에서 이메일을 바꾼 사용자가 새 계정을 받으면 그 사람의 학습
레이어가 끊긴다. 이메일에 UNIQUE도 걸지 않는다 — 한 사람이 두 제공자로 들어올 수 있고, 이메일 일치를
근거로 자동 병합하면 제공자가 미검증 이메일을 준 경우 계정 탈취가 된다.

**사용자 체인도 CSRF를 켜지 않는다.** 설계 문서는 "사용자 체인은 쿠키를 쓸 수 있어 켜 둔다"였는데,
리프레시 토큰 없이 무상태 Bearer로 확정했으므로 브라우저가 자동 전송하는 자격 증명이 없다 — 전제가
사라졌다. 대가는 리프레시가 없다는 점이고, 그래서 사용자 토큰 TTL이 관리자보다 길다(7일 vs 8시간).

**사용자 API는 `USER` 역할을 요구한다.** `authenticated()`만 두면 관리자 토큰도 통과하는데, 사용자
API는 토큰 subject를 사용자 ID로 읽으므로 이메일이 들어오면 파싱하다 실패한다 — 인가 구멍이 500으로
위장된다. 두 방향 모두 테스트로 고정했다.

### P3.2 그래프 탐색 API

- [ ] Neo4j 기반 챕터 그래프 조회
- [ ] 임의 지점 진입 · 연관 챕터 탐색

### P3.3 챕터 조회 API — 합성

- [ ] `뼈대 블록 문서 + 사용자 레이어` → 개인화된 블록 문서 반환
- [ ] REST, 챕터 단위
- [ ] **HTML을 만들지 않는다** — 서버가 내리는 것은 블록 문서다

> "백엔드 합성"은 **레이어 병합**이지 HTML 생성이 아니다. 서버가 렌더까지 하면 모바일·태블릿
> 앱을 붙일 때 API를 다시 만들어야 한다. M3 시점에는 레이어가 비어 있어 합성이 항등에 가깝지만,
> 경계는 지금 그어 둔다.

### P3.4 캐시

- [ ] Redis, 키에 **버전과 형태 포함** — `chapter:{id}:v{version}:{format}`
- [ ] 무효화 로직 없음. 구버전 키는 TTL로 자연 만료

명시적 무효화를 쓰지 않는 이유는 삭제 호출이 한 번만 누락돼도 사용자가 구버전을 계속 보게 되고
그게 **에러 없이 조용히 틀리기** 때문이다.

### P3.5 React 렌더러

- [ ] 블록 타입별 렌더 — `heading / paragraph / figure / formula / quiz`
- [ ] `figure` 시각화(그래프 · 인포그래픽) 렌더
- [ ] `narration`은 웹에서 렌더하지 않는다 (영상 전용 블록)

### P3.6 신호 수집

- [ ] 신호 레코드 `{ chapterId, chapterVersion, blockId, format, type, payload, userId, at }`
- [ ] **개인 루프** — Postgres 동기 기록
- [ ] **집단 루프** — Kafka 발행
- [ ] 수집 대상: 퀴즈 응답, 질문, 오류 신고, 소비 진행
- [ ] `chapterVersion`은 **사용자가 실제로 소비한 버전**을 기록

> `blockId`가 없으면 집단 루프의 정밀도가 챕터 단위로 떨어져 "이 챕터가 어렵다"까지만 알 수 있다.
> 어느 문단·어느 수식에서 막히는지가 나와야 수정안이 만들어진다. 이 페이즈는 M5의 전제다.
>
> 신호를 전부 Kafka로만 흘리면 개인 루프가 최종 일관성이 되어 "방금 답한 결과가 다음 챕터에
> 반영되지 않는" 타이밍 문제가 생긴다. 그래서 두 경로다.

### P3.7 시드 카탈로그 투입

- [ ] 도메인 1~2개, 분야 5~10개, 주제 **소수(3~5개)**로 시작해 파이프라인 검증
- [ ] 소비 가능한 상태 확인 후 확대 — 전량 30~50개는 M7 P7.2

넓고 얕게 펴지 않는다. 초기 사용자가 적은데 주제를 넓게 벌리면 뼈대당 사용자가 1~2명씩 붙어
집단 루프가 영원히 임계치를 못 넘는다.
