## 목표

**사용자가 실제로 소비하고, 여기서부터 신호가 발생한다.**

로드맵 전체에서 가장 중요한 전환점이다. M2까지는 만드는 이야기였고 M3부터는 **데이터가 쌓인다.**
M4·M5·M6가 전부 여기서 나오는 신호와 콘텐츠에 의존한다.

## 완료 기준 (DoD)

- [ ] 소셜 로그인 → 주제 진입 → 그래프 탐색 → 챕터 소비까지 끊김 없이 동작한다
- [ ] 퀴즈 응답 · 질문 · 오류 신고가 **블록 ID와 딜리버리 형태를 달고** 신호로 기록된다
- [ ] 같은 챕터 재조회가 캐시에서 나오고, 뼈대가 수정되면 무효화 호출 없이 새 버전이 나온다
- [ ] 시드 주제로 실제 학습이 가능하다

## 페이즈

### P3.1 사용자 인증 ✅

- [x] OAuth2 소셜 로그인 → JWT — **Google · Kakao**, 인가 코드 교환은 서버가 한다
- [x] 관리자 경로(M1 P1.2)와 분리된 채로 공존 — 필터 체인 두 개, 역할로 구분(`USER` / `ADMIN`)
- [x] `users` 테이블 (V13). 정체성은 `(제공자, 제공자 식별자)`, 비밀번호 컬럼 없음
- [x] `GET /api/auth/providers` · `POST /api/auth/social/{provider}` · `GET /api/auth/me`

**인가 코드를 서버가 교환한다.** 클라이언트가 제공자 토큰을 직접 받아 넘기면 서버는 그 토큰이 우리
앱을 위해 발급된 것인지 확인할 방법이 없고, 클라이언트가 웹·모바일·태블릿으로 늘어날 때마다 제공자
SDK와 시크릿 취급 규칙이 하나씩 생긴다.

**정체성은 이메일이 아니다.** 제공자 쪽에서 이메일을 바꾼 사용자가 새 계정을 받으면 그 사람의 학습
레이어가 끊긴다. 이메일에 UNIQUE도 걸지 않는다 — 한 사람이 두 제공자로 들어올 수 있고, 이메일 일치를
근거로 자동 병합하면 제공자가 미검증 이메일을 준 경우 계정 탈취가 된다.

**사용자 체인도 CSRF를 켜지 않는다.** 설계 문서는 "사용자 체인은 쿠키를 쓸 수 있어 켜 둔다"였는데,
리프레시 토큰 없이 무상태 Bearer로 확정했으므로 브라우저가 자동 전송하는 자격 증명이 없다 — 전제가
사라졌다. 대가는 리프레시가 없다는 점이고, 그래서 사용자 토큰 TTL이 관리자보다 길다(7일 vs 8시간).

**사용자 API는 `USER` 역할을 요구한다.** `authenticated()`만 두면 관리자 토큰도 통과하는데, 사용자
API는 토큰 subject를 사용자 ID로 읽으므로 이메일이 들어오면 파싱하다 실패한다 — 인가 구멍이 500으로
위장된다. 두 방향 모두 테스트로 고정했다.

### P3.2 그래프 탐색 API ✅

- [x] Neo4j 기반 챕터 그래프 조회 — `LoadChapterGraphPort`, 가변 길이 패턴 탐색
- [x] 임의 지점 진입 · 연관 챕터 탐색 — `GET /api/{topics|skeletons}/{id}/entry-points`,
      `GET /api/chapters/{id}/neighbors?depth=`
- [x] **published 뼈대만** 답한다. 검수용 조회(`/api/admin/skeletons/{id}/graph`)와 별 엔드포인트
- [x] 사용자 주제 입력 경로(`POST /api/topics/resolve`)를 열었다 — M1 이 M3 로 미룬 것
- [x] 주제 해소 레이트 리밋 (Redis 고정 창)

**탐색을 Neo4j 에 묻는 이유는 질문이 가변 길이이기 때문이다.** "이 챕터에서 N홉 이내"를 Postgres 에
물으면 홉 수만큼 조인이 붙는다. 반대로 **공개 여부는 Postgres 에 묻는다** — Neo4j 는 파생 저장소라
반영이 뒤처질 수 있고, 그 지연이 접근 판정에 섞이면 "잠깐 열렸다 닫히는" 상태가 만들어진다.

**진입점은 선행이 *들어오지 않는* 챕터다.** RELATED 로만 연결된 챕터는 진입점이다 — 관계가 있다는
사실만으로 막으면 곁가지 주제로 바로 시작할 수 없다.

**그래프에 노드가 없으면 빈 이웃이 아니라 404 다.** 둘을 같게 두면 파생 저장소 유실이 "관련 챕터
없음"으로 보이고, 그건 에러 없이 조용히 틀린다. 홉 수는 상한(3)으로 접히고 **접힌 값이 응답에
실린다** — 요청값을 되돌려주면 접혔다는 사실을 클라이언트가 알 수 없다.

**사용자 주제 입력을 여기서 연 이유**는 DoD 1번의 사슬(로그인 → 주제 진입 → 그래프 탐색 → 소비)이
진입 없이 이어지지 않기 때문이다. M1 이 이 경로를 미룬 조건이 둘이었고 둘 다 갖췄다 — 소셜
로그인(P3.1)과 레이트 리밋. 호출 하나가 LLM 을 최대 3번 부르므로 그 둘 없이 열면 비용 남용 경로가
그대로 생긴다. 리밋 카운터는 Redis 다. 프로세스 메모리에 두면 한도가 **인스턴스 수만큼 곱해지고**
그 느슨함은 에러 없이 생긴다. 저장소가 죽으면 막는다(fail-closed) — 통과시키면 그 순간이 비용 폭주
창구다. 일반적인 엔드포인트 리밋은 M7 의 몫이다.

**요청 토큰(`requestId`)의 소유권을 확인한다.** 없으면 다른 사용자의 대기 중인 요청을 확정할 수 있고,
그건 남의 입력을 엉뚱한 주제로 수렴시키면서 신규 뼈대 생성까지 대신 트리거하는 것이다. 없는 것과 남의
것을 같은 404 로 접는다 — 나누면 응답만으로 requestId 를 열거할 수 있다.

### P3.3 챕터 조회 API — 합성 ✅

- [x] `뼈대 블록 문서 + 사용자 레이어` → 개인화된 블록 문서 반환 — `LayerComposition`
- [x] REST, 챕터 단위 — `GET /api/chapters/{id}?format=WEB`
- [x] **HTML을 만들지 않는다** — 서버가 내리는 것은 블록 목록이다
- [x] `DeliveryFormat`(WEB/VIDEO/PRESENTATION) — 웹만 `narration`을 걸러 낸다
- [x] 보충 블록 ID 공간 분리 (`b{n}` 공용 / `s{n}` 개인화)
- [x] published 검사를 `PublishedSkeletonGuard` 한 곳으로 모았다

> "백엔드 합성"은 **레이어 병합**이지 HTML 생성이 아니다. 서버가 렌더까지 하면 모바일·태블릿
> 앱을 붙일 때 API를 다시 만들어야 한다. M3 시점에는 레이어가 비어 있어 합성이 항등에 가깝지만,
> 경계는 지금 그어 둔다.

**합성 함수가 *할 수 없는 일*이 설계의 핵심이다.** `LayerComposition`은 본문 블록을 바꾸거나 지울
경로가 없다 — 기존 `Block` 인스턴스를 새 목록에 옮기고 사이에 보충 블록을 끼우는 것뿐이다. 규칙으로
두면 언젠가 깨지므로 구조로 막았다. 본문이 사용자마다 달라지는 순간 집단 루프가 작동을 멈춘다.

**보충 블록의 ID 공간을 공용 본문과 나눴다.** 같은 공간을 쓰면 어떤 사용자의 보충 블록 `b7`에 붙은
신호가 공용 본문 `b7`의 신호와 섞인다. 그 오염은 에러 없이 임계치 판정과 수정 전후 비교를 동시에
무너뜨린다. 공용 블록 문서는 `s{n}`을 아예 담을 수 없다(저장 경로에서 거절).

**앵커가 없는 보충 블록은 버린다.** 앵커가 사라졌다는 것은 그 문단이 수정으로 없어졌다는 뜻이고,
끝에 몰아 붙이면 맥락 없는 곳에 설명이 나타난다.

**레이어는 아직 비어 있다** — 적재는 P4.1이 붙이고, 그 자리는 `ChapterCompositionService`에
표시해 뒀다. 경계를 지금 그은 이유는, 나중에 그으려면 "본문을 그대로 내리는" 코드가 이미 호출부마다
퍼져 있기 때문이다. 합성 규칙 자체는 이 페이즈에서 전부 검증된다.

**본문 없는 published 챕터는 빈 목록이 아니라 404다.** published 전환 조건이 "전 챕터 완료"이므로
그 상태는 정상이 아니고, 빈 목록으로 내리면 "내용 없는 챕터"로 보인다.

**곁가지 발견**: 잘못된 enum 쿼리 파라미터가 500으로 나가고 있었다(`?format=HOLOGRAM`).
`MethodArgumentTypeMismatchException` → 400 핸들러를 더했다 — 입력 오류가 서버 오류로 보이면
운영자가 고칠 것 없는 알림을 계속 받고 진짜 오류가 그 사이에 묻힌다.

### P3.4 캐시 ✅

- [x] Redis, 키에 **버전과 형태 포함** — `chapter:100:v2:web`
- [x] 무효화 로직 없음. 구버전 키는 TTL로 자연 만료 (`nextchapter.cache.chapter-ttl`, 기본 24h)
- [x] 캐시 대상은 **공용 문서**다 — 합성은 캐시 조회 뒤에 온다
- [x] 포트에 무효화 메서드 자체를 두지 않았다

명시적 무효화를 쓰지 않는 이유는 삭제 호출이 한 번만 누락돼도 사용자가 구버전을 계속 보게 되고
그게 **에러 없이 조용히 틀리기** 때문이다.

**버전을 챕터 행에서 읽어 키를 만든다.** 그래서 캐시 히트일 때 본문 스냅샷(JSONB)을 읽지 않는다 —
이 조회에서 가장 비싼 부분이 그것이다. 챕터 행과 버전 스냅샷은 같은 트랜잭션에서 쓰이므로 두 값이
어긋나지 않는다.

**캐시 실패는 조회를 막지 않는다.** 캐시는 파생이고 원천은 Postgres다 — Redis가 죽었을 때 학습이
멈추는 것은 받아들일 수 없다. 레이트 리밋(P3.2)이 반대로 fail-closed인 것과 대조되는데, 그쪽은
실패가 **비용**으로 나타나고 이쪽은 **느려지는** 것으로 나타나기 때문이다. 역직렬화 실패도 미스로
접는다 — 배포로 블록 모양이 바뀌었을 때 예외를 올리면 배포 직후 모든 챕터 조회가 실패한다.

**형태별로 걸러 저장한다.** 형태가 키에 있으므로 값에 다른 형태의 블록이 섞이면 안 된다 — 웹
사용자가 `narration`이 섞인 목록을 받는 것이 그 실패다.

> 개인화된 합성 결과를 캐시하지 않는 경계는 P4.5의 항목이지만, 캐시를 넣는 이 지점에서 이미
> 코드로 갈라져 있다. 나중에 나누려면 그때는 이미 개인화 결과가 공용 키에 들어가 있다.

### P3.5 React 렌더러 ✅

- [x] 블록 타입별 렌더 — `heading / paragraph / figure / formula / quiz`
- [x] `figure` 시각화 렌더 — `spec`을 SVG 막대 그래프로, 모르는 명세는 표로
- [x] `narration`은 웹에서 렌더하지 않는다 (서버가 걸러 내고, 클라이언트도 건너뛴다)
- [x] 로그인(제공자 버튼을 서버에서 받는다) → 주제 진입 → 진입점 → 챕터 → 이웃 탐색
- [x] 블록마다 붙는 질문·오류 신고 도구 + 퀴즈 응답 + 소비 진행 신호
- [x] `GET /api/auth/providers`가 **동의 화면 주소까지** 내려 준다

**동의 화면 주소를 서버가 조립한다.** 클라이언트가 만들면 `client_id`를 프론트엔드에 박아야 하고,
제공자를 추가할 때 서버와 클라이언트를 함께 고쳐야 한다 — 그러면 "설정은 됐는데 버튼이 없다"거나 그
반대인 상태가 생긴다. `state`에는 임의 값과 **제공자 이름**을 함께 담는다. 제공자는 콜백에 자기 이름을
돌려주지 않고, 콜백 주소를 제공자마다 다르게 두면 제공자 콘솔에 주소를 하나 더 등록해야 한다.

**질문 UI를 블록에 앵커링했다** — "여기서 정해야 할 것"의 두 번째 항목이 이렇게 정해졌다. 블록마다 질문·
오류 신고 버튼이 붙고, 그 버튼이 만드는 신호가 그 블록 ID를 단다. 챕터 전체에 붙는 입력창을 두지 않은
이유는 그러면 집단 루프가 "이 챕터가 어렵다"까지만 알 수 있기 때문이다.

**모르는 블록 타입은 조용히 건너뛰지 않고 표시할 수 없다고 알린다.** 건너뛰면 클라이언트가 서버보다
오래된 상태에서 콘텐츠가 빠진 것을 사용자가 알 수 없다. 같은 이유로 그릴 수 없는 `figure` 명세는 값을
표로 보여 준다.

**수식은 LaTeX 원문을 그대로 보여 준다.** 렌더 라이브러리(KaTeX 등)는 번들 크기·PPT 재사용과 얽혀
되돌리기 어려운 선택이라 딜리버리 확장(M6)에서 함께 정한다. 차트 라이브러리도 같은 이유로 넣지 않고
SVG를 직접 그렸다.

**여기서 발견한 결함 — 퀴즈 정답이 브라우저로 내려가고 있었다.** 클라이언트가 정답을 알면 채점을
클라이언트가 하게 되고 그 결과는 위조할 수 있다. 오답률은 집단 루프의 핵심 신호이므로 위조 가능성 자체가
임계치 판정과 수정 전후 비교의 근거를 없앤다 — 그리고 그건 에러 없이 일어난다. 고쳤다.

- 사용자 응답에서 정답 속성을 뺀다 (`BlockView.forLearner`). 운영자 응답은 그대로 — 검수는 정답을
  봐야 성립한다
- 클라이언트는 **고른 답만** 보내고 서버가 원천(버전 스냅샷)에서 정답을 읽어 채점한다
- 채점 결과를 응답에 실어 준다. 정답을 숨기면 결과를 알려 줘야 화면이 성립한다
- 정답 비교는 문자열로 한다 — 정답이 JSON에서 숫자로, 고른 답이 문자열로 올 수 있고 그 차이로 정답을
  오답으로 세면 오답률이 조용히 부풀려진다

### P3.6 신호 수집 ✅

> **P3.5보다 먼저 했다.** 프론트엔드가 렌더와 동시에 신호를 붙여야 하므로, 기록 API가 먼저 있으면
> 클라이언트를 한 번에 배선할 수 있다. 페이즈를 지우거나 합치지 않고 순서만 바꿨다.

- [x] 신호 레코드 `{ chapterId, chapterVersion, blockId, format, type, payload, userId, at }` (V14)
- [x] **개인 루프** — Postgres 동기 기록 (같은 트랜잭션)
- [x] **집단 루프** — Kafka 발행 (`signal.consumption.recorded`, 키는 챕터 ID)
- [x] 수집 대상: 퀴즈 응답, 질문, 오류 신고, 소비 진행 — `POST /api/chapters/{id}/signals` 하나로
- [x] `chapterVersion`은 **사용자가 실제로 소비한 버전**을 기록

> `blockId`가 없으면 집단 루프의 정밀도가 챕터 단위로 떨어져 "이 챕터가 어렵다"까지만 알 수 있다.
> 어느 문단·어느 수식에서 막히는지가 나와야 수정안이 만들어진다. 이 페이즈는 M5의 전제다.
>
> 신호를 전부 Kafka로만 흘리면 개인 루프가 최종 일관성이 되어 "방금 답한 결과가 다음 챕터에
> 반영되지 않는" 타이밍 문제가 생긴다. 그래서 두 경로다.

**`signals` 테이블이 곧 집단 루프의 outbox다.** 행 자체가 이벤트이므로 별도 테이블을 두지 않고
`published_at`을 붙였다. 커밋 뒤에 바로 발행하고 실패를 로그로만 남기면 그 신호는 집계에 영원히
도달하지 않고, 그 유실은 **"임계치가 트리거되지 않는다"로 조용히** 나타난다. 발행과 발행 표시를 같은
트랜잭션에 두므로 중복 발행은 가능하지만 누락은 없다.

**필수 페이로드를 타입이 들고 있다.** 정답 여부 없는 퀴즈 응답은 오답률을 만들지 못하고, 본문 없는
질문은 "같은 지점에서 묻는다"를 판정할 수 없다 — 그런 신호는 저장돼도 집계에 기여하지 않으면서 건수만
늘린다. `PROGRESS`만 블록 없이 기록된다(본래 챕터 단위 사실이다).

**blockId가 그 버전에 실재하는지 확인한다.** 없는 블록에 붙은 신호는 "질문은 많은데 고칠 지점을 찾을 수
없는" 상태를 만든다. 확인은 **소비한 버전**으로 한다 — 최신 버전으로 확인하면 읽는 사이에 수정이 반영된
사용자의 정상 신호가 거절된다. 검증에 필요한 문서는 P3.4의 캐시를 그대로 쓴다(`SharedChapterDocuments`).

**보충 블록(`s{n}`)에 붙은 신호는 통과시키되 구분해 발행한다.** 그 블록은 그 사람의 레이어에만 있으므로
공용 문서에서 찾을 수 없고, 거절하면 개인화 블록에 대한 질문을 받을 수 없다.

**곁가지 발견**: 없는 enum 값이 담긴 JSON 본문이 500으로 나가고 있었다.
`HttpMessageNotReadableException` → 400 핸들러를 더했다. 예외 메시지는 내보내지 않는다 — Jackson의
메시지에 보낸 값 일부가 들어 있고, 그 값이 질문·오류 신고 본문일 수 있다.

### P3.7 시드 카탈로그 투입

- [ ] 도메인 1~2개, 분야 5~10개, 주제 **소수(3~5개)**로 시작해 파이프라인 검증
- [ ] 소비 가능한 상태 확인 후 확대 — 전량 30~50개는 M7 P7.2

집단 루프가 영원히 임계치를 못 넘는다.
