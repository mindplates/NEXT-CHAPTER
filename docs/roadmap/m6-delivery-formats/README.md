## 목표

**한 소스가 웹 · 영상 · PPT 세 형태로 뻗는다.**

형태별로 콘텐츠를 따로 생성하지 않는다. 소스가 하나여야 여러 사람의 반응을 겹쳐 볼 수 있고,
소스가 하나여야 여러 형태로 뻗을 수 있다. M2에서 만든 블록 문서를 **렌더링**하는 것이지 다시
생성하는 것이 아니다.

## 왜 여기에 있는가

로드맵은 딜리버리 형태 우선순위를 **웹 먼저**로 놓았다. 3개월 필수 기준이 집단 루프 1회전이지
딜리버리 다양성이 아니기 때문이다. 자세한 근거는 [로드맵 개요](../#이-로드맵이-전제하는-결정)에 있다.

`published` 조건은 **활성화된 형태 전부 완료**로 읽는다. M6가 끝나면 활성 형태가 3개가 되고
조건이 자동으로 확장된다. 형태를 나중에 켠다는 것이지 완결성을 포기한다는 뜻이 아니다.

## 완료 기준 (DoD)

- [ ] 챕터 하나가 웹 · 영상 · PPT 세 형태로 제공된다
- [ ] 챕터가 수정되어도 형태가 잠기지 않고, **완료된 자산 중 최신 버전**이 계속 서빙된다
- [ ] 새 버전 자산이 완성되면 별도 전환 작업 없이 자동으로 교체된다
- [ ] 신호의 `format`으로 형태별 오답률 분해가 가능하다

## 페이즈

### P6.1 오브젝트 스토리지와 자산 메타

- [ ] `adapter/storage` — 오브젝트 스토리지 어댑터
- [ ] 자산 메타 스키마: 형태, **자신의 기준 `chapterVersion`**, 스토리지 키, 생성 상태
- [ ] 바이너리는 DB에 넣지 않는다 — Postgres에는 메타만

### P6.2 ④ 파생 자산 파이프라인

- [ ] `skeleton.asset.requested` — 챕터 × 형태만큼 발행
- [ ] **형태별로 토픽 · 파티션 분리**
- [ ] 뼈대 수정 시에도 이 단계를 다시 돈다

영상은 TTS와 렌더링이 붙어 다른 단계와 소요시간의 자릿수가 다르다. 형태를 섞어 두면 무거운
형태가 가벼운 형태를 막는다.

### P6.3 이미지 · 도표

- [ ] `figure` 블록 → 이미지 · 그래프 · 인포그래픽 생성
- [ ] 웹에서도 쓰이므로 M3와 겹치는 부분 정리

### P6.4 영상 강의

- [ ] `narration` 블록 → TTS
- [ ] 자막 생성
- [ ] 강의 자료 + 음성 + 자막 → 영상 렌더

### P6.5 프레젠테이션

- [ ] 블록 문서 → 슬라이드 변환
- [ ] 다운로드 · 발표 모드

### P6.6 자산 버전 서빙

- [ ] 조회 시 **완료된 자산 중 `chapterVersion` 최댓값** 선택
- [ ] 새 버전 완성 시 자동 교체
- [ ] `published` 조건을 활성 형태 기준으로 일반화

> 형태를 "일시 중단"하면 개선이 잦을수록 영상을 볼 수 없는 시간이 늘어나, **개선 루프가 잘 돌수록
> 서비스가 나빠지는 역전**이 생긴다. 그래서 잠그지 않는다.

### P6.7 형태별 신호 분해

- [ ] 신호의 `format`으로 형태별 오답률 리포트
- [ ] M5 P5.3의 수정안 근거에 연결
- [ ] `chapterVersion`이 **소비한 버전**으로 기록되는지 재확인

> 영상은 자산 버전이 뒤처져 있을 수 있다. 무조건 최신 챕터 버전으로 기록하면 구버전 영상을 본
> 사람의 오답이 최신 버전의 실패로 잘못 집계되어, M5 P5.6의 전후 비교가 오염된다.
