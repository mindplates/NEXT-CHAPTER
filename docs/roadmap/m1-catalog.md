## 목표

**자유 입력이 정확히 하나의 뼈대로 수렴한다.**

생성보다 매핑을 먼저 만드는 이유는 순서를 뒤집으면 되돌릴 수 없기 때문이다. 매핑 없이 생성부터
열면 "머신러닝"과 "기계학습"이 각각 뼈대를 만들고, 그 뒤에 병합하려면 이미 갈라진 신호를 손으로
합쳐야 한다. 주제 통합은 부가 기능이 아니라 **개선 루프의 전제조건**이다.

## 완료 기준 (DoD)

- [ ] "머신러닝", "기계학습", "ML 입문", "머신러닝 배우고 싶어"가 **같은 주제 ID**로 수렴한다
- [ ] 매칭 실패 시 유사 주제 후보가 제시되고, 사용자가 전부 거절해야만 신규 주제가 등록된다
- [ ] 관리자가 단계별 벤더·모델·API 키를 화면에서 지정할 수 있고, 코드에 하드코딩된 모델이 없다
- [ ] 임베딩 모델을 교체하면 재임베딩 배치로 전량 갱신된다

## 페이즈

### P1.0 공통 기반 ✅

페이즈 번호가 없던 선행 작업이다. P1.1을 시작하자마자 필요해져 함께 넣었다.

- [x] `nextchapter-common` — `exception` / `response.ApiResponse` / `time.AppTime` / `text.Strings`
- [x] `GlobalExceptionHandler` — 예외 → HTTP 매핑을 한 곳에. **마지막 핸들러는 예외 메시지를 그대로
      내보내지 않는다** (드라이버 오류·쿼리 조각·경로가 섞여 나온다)
- [x] **Flyway** — 스키마의 원천을 마이그레이션 SQL로. `ddl-auto=none` 유지

Boot 4는 자동설정을 기술별 모듈로 쪼갰다. `flyway-core`만 넣으면 마이그레이션이 **조용히 실행되지
않으므로** `spring-boot-flyway`를 함께 넣는다 — M0의 Kafka(`spring-kafka` → starter)와 같은 함정이다.

### P1.1 카탈로그 스키마와 CRUD ✅

- [x] `도메인 > 분야 > 주제` 3단계 테이블 (`V1__catalog.sql`)
- [x] 주제에 뼈대가 **1:1**로 붙는 제약 — `skeletons.topic_id` UNIQUE
- [x] 관리자용 CRUD API — `/api/admin/catalog/**`, 트리 조회 포함
- [x] 주제 별칭 테이블 — 자유 입력 수렴의 결정적 경로 (P1.5가 LLM 앞단에서 쓴다)

4단계로 늘리지 않는다. 4번째 층은 이미 뼈대 안의 챕터 그래프가 표현하는 층위이고, 분류로 한 번 더
쪼개면 뼈대가 갈라져 신호가 분산된다.

**slug 유일성의 범위를 계층마다 다르게 뒀다.** 주제는 전역 유일, 분야는 도메인 안에서만 유일이다.
뼈대가 붙는 곳은 주제뿐이라 주제가 두 벌 생기는 것이 곧 신호 분산이지만, 분야는 갈라져도 신호에
영향이 없다 — 반대로 수학 > 통계와 컴퓨터과학 > 통계를 금지하면 카탈로그가 부자연스러워진다.

**1:1 제약을 DB에 뒀다.** 애플리케이션 검사만으로는 동시 요청 두 건이 같은 주제로 뼈대를 두 개
만든다. Testcontainers 테스트가 실제로 두 번째 삽입이 막히는 것을 확인한다.

### P1.2 관리자 인증 ✅

- [x] 자체 계정 + JWT, 역할 `ADMIN` (`V2__admin_accounts.sql`)
- [x] 사용자 인증(소셜)과 **경로 분리** — `adapter/security`, 필터 체인 2개
- [x] 최초 관리자 계정 부트스트랩 — 계정이 0개일 때만
- [x] 로그인 실패 사유를 구분하지 않음 — 응답으로 계정을 열거할 수 없게

관리자 인증을 여기서 먼저 만드는 이유는 관리 화면(P1.3, P1.6)이 이것 없이는 열리지 않기 때문이다.
사용자 소셜 로그인은 소비가 시작되는 M3로 미룬다.

JWT 발급·검증을 직접 만들지 않고 `oauth2-resource-server`의 `NimbusJwtEncoder`/`Decoder`와
`oauth2ResourceServer` DSL을 쓴다. 직접 만든 필터는 **"만료 확인 한 줄을 빠뜨려도 통과하는"** 실패
방식을 갖는다.

### P1.3 AI 프로바이더 추상화

- [ ] 프로바이더 인터페이스 (`adapter/ai`), 벤더 교체 가능한 구조
- [ ] 단계별 벤더·모델 설정 — 뼈대 본문 생성 / 주제 매핑·분류 / 검증 패스 / 개인화 보충 블록
- [ ] API 키 등록·교체를 관리 화면에서 (코드·환경변수 하드코딩 금지)
- [ ] 기본값 전 단계 `claude-opus-5`

### P1.4 주제 임베딩 (pgvector)

- [ ] 주제 임베딩을 **PostgreSQL pgvector**에 저장 (주제 메타와 같은 트랜잭션)
- [ ] 유사도 검색
- [ ] **재임베딩 배치 경로** — 모델 교체 시 전량 무효화 후 재생성

> 재임베딩을 나중으로 미루면 안 된다. 모델을 관리 화면에서 교체할 수 있게 만든 순간 재임베딩은
> *언젠가 필요한 것*이 아니라 *반드시 일어나는 것*이 된다. 경로가 없으면 교체 기능이 거짓말이 된다.

### P1.5 입력 → 뼈대 매핑

- [ ] LLM이 `도메인 → 분야 → 주제` 순으로 단계적 매핑
- [ ] 각 단계 후보를 수십 개 이내로 유지 (층별 좁히기)
- [ ] 매칭 시 기존 뼈대에 합류
- [ ] 미매칭 시 **유사 주제 후보 제시 → 사용자 확인** → 전부 거절 시에만 신규 주제 등록

사용자를 통합의 마지막 판정자로 세운다. 자동 생성으로 흘리면 오매칭 방지망이 없고, 운영자 승인
대기열로 보내면 사용자가 그 자리에서 학습을 시작할 수 없다.

### P1.6 미매핑 입력 검토

- [ ] 매칭 실패한 입력 로그
- [ ] 관리자 검토 화면 — 카탈로그에 반영하거나 기각

## 여기서 정한 것

확정된 결정은 `CLAUDE.md`로 옮겼다. 아래는 그 요약이다.

| 항목 | 결정 |
|------|------|
| 스키마 관리 | Flyway 마이그레이션이 원천, `ddl-auto=none`. 제약은 DB에 둔다 |
| slug 유일성 | 주제는 전역, 분야는 도메인 내, 도메인은 전역. slug는 생성 후 불변 |
| 주제 수렴 1차 경로 | 별칭 테이블 + NFKC 정규화. 정규화 값은 전역 유일 |
| 인증 경로 분리 | 필터 체인 2개. 관리자 체인만 CSRF 끔(무상태 Bearer) |
| 최초 관리자 | 계정 0개일 때만 설정값으로 생성. JWT 서명키 기본값 없음 |

## 여기서 정해야 할 것

| 항목 | 비고 |
|------|------|
| 임베딩 모델 기본값 | 프로바이더 설정의 한 단계로 들어간다 (P1.3 · P1.4) |
| 후보 제시 개수 · 유사도 컷오프 | 컷오프가 낮으면 오매칭, 높으면 불필요한 신규 뼈대 (P1.5) |
| 커버리지 80% 게이트 | M0에서 M1으로 넘긴 항목. **M1 전 페이즈 완료 후 건다** — 중간에 걸면 페이즈마다 빨간불이 된다 |
