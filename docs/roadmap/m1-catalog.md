## 목표

**자유 입력이 정확히 하나의 뼈대로 수렴한다.**

생성보다 매핑을 먼저 만드는 이유는 순서를 뒤집으면 되돌릴 수 없기 때문이다. 매핑 없이 생성부터
열면 "머신러닝"과 "기계학습"이 각각 뼈대를 만들고, 그 뒤에 병합하려면 이미 갈라진 신호를 손으로
합쳐야 한다. 주제 통합은 부가 기능이 아니라 **개선 루프의 전제조건**이다.

## 완료 기준 (DoD)

- [ ] 매칭 실패 시 유사 주제 후보가 제시되고, 사용자가 전부 거절해야만 신규 주제가 등록된다
- [ ] 관리자가 단계별 벤더·모델·API 키를 화면에서 지정할 수 있고, 코드에 하드코딩된 모델이 없다
- [x] 임베딩 모델을 교체하면 재임베딩 배치로 전량 갱신된다

## 페이즈

### P1.0 공통 기반 ✅

페이즈 번호가 없던 선행 작업이다. P1.1을 시작하자마자 필요해져 함께 넣었다.

- [x] `nextchapter-common` — `exception` / `response.ApiResponse` / `time.AppTime` / `text.Strings`
- [x] `GlobalExceptionHandler` — 예외 → HTTP 매핑을 한 곳에. **마지막 핸들러는 예외 메시지를 그대로
      내보내지 않는다** (드라이버 오류·쿼리 조각·경로가 섞여 나온다)
- [x] **Flyway** — 스키마의 원천을 마이그레이션 SQL로. `ddl-auto=none` 유지

Boot 4는 자동설정을 기술별 모듈로 쪼갰다. `flyway-core`만 넣으면 마이그레이션이 **조용히 실행되지
않으므로** `spring-boot-flyway`를 함께 넣는다 — M0의 Kafka(`spring-kafka` → starter)와 같은 함정이다.

### P1.1 카탈로그 스키마와 CRUD ✅

- [x] `도메인 > 분야 > 주제` 3단계 테이블 (`V1__catalog.sql`)
- [x] 주제에 뼈대가 **1:1**로 붙는 제약 — `skeletons.topic_id` UNIQUE
- [x] 관리자용 CRUD API — `/api/admin/catalog/**`, 트리 조회 포함
- [x] 주제 별칭 테이블 — 자유 입력 수렴의 결정적 경로 (P1.5가 LLM 앞단에서 쓴다)

4단계로 늘리지 않는다. 4번째 층은 이미 뼈대 안의 챕터 그래프가 표현하는 층위이고, 분류로 한 번 더
쪼개면 뼈대가 갈라져 신호가 분산된다.

**slug 유일성의 범위를 계층마다 다르게 뒀다.** 주제는 전역 유일, 분야는 도메인 안에서만 유일이다.
뼈대가 붙는 곳은 주제뿐이라 주제가 두 벌 생기는 것이 곧 신호 분산이지만, 분야는 갈라져도 신호에
영향이 없다 — 반대로 수학 > 통계와 컴퓨터과학 > 통계를 금지하면 카탈로그가 부자연스러워진다.

**1:1 제약을 DB에 뒀다.** 애플리케이션 검사만으로는 동시 요청 두 건이 같은 주제로 뼈대를 두 개
만든다. Testcontainers 테스트가 실제로 두 번째 삽입이 막히는 것을 확인한다.

### P1.2 관리자 인증 ✅

- [x] 자체 계정 + JWT, 역할 `ADMIN` (`V2__admin_accounts.sql`)
- [x] 사용자 인증(소셜)과 **경로 분리** — `adapter/security`, 필터 체인 2개
- [x] 최초 관리자 계정 부트스트랩 — 계정이 0개일 때만
- [x] 로그인 실패 사유를 구분하지 않음 — 응답으로 계정을 열거할 수 없게

관리자 인증을 여기서 먼저 만드는 이유는 관리 화면(P1.3, P1.6)이 이것 없이는 열리지 않기 때문이다.
사용자 소셜 로그인은 소비가 시작되는 M3로 미룬다.

JWT 발급·검증을 직접 만들지 않고 `oauth2-resource-server`의 `NimbusJwtEncoder`/`Decoder`와
`oauth2ResourceServer` DSL을 쓴다. 직접 만든 필터는 **"만료 확인 한 줄을 빠뜨려도 통과하는"** 실패
방식을 갖는다.

### P1.3 AI 프로바이더 추상화 ✅

- [x] 프로바이더 인터페이스 (`adapter/ai`) — `LlmCompletionClientPort` · `EmbeddingClientPort`
- [x] 단계별 벤더·모델 설정 (`V3__ai_provider.sql`) — 본문 생성 / 주제 매핑 / 검증 / 개인화 / **임베딩**
- [x] API 키 등록·교체를 관리 화면에서. **AES-GCM 암호문으로 저장**
- [x] 기본값 전 단계 `claude-opus-5` — Java 상수가 아니라 마이그레이션이 심는 행으로
- [x] `AiGateway` — 호출부는 단계 이름만 안다. 벤더·모델·키를 모른다

**임베딩 단계를 추가했다.** 설계 문서의 4단계에 없던 것인데, 재임베딩 경로(P1.4)가 "지금 어느 모델을
쓰는가"를 설정에서 읽어야 하기 때문이다. 모델을 코드에 두면 교체가 곧 배포가 된다.

**임베딩만 벤더가 다르다 — Anthropic 은 임베딩 API 를 제공하지 않는다.** "전 단계 Claude Opus 5"를
임베딩에도 적으면 설정은 그럴듯한데 호출이 실패한다. 기본값을 Voyage(`voyage-3-large`)로 뒀고, 이
두 번째 구현이 프로바이더 추상화의 실증도 겸한다 — 벤더 추가 비용이 "포트 구현 하나"임을 확인했다.

**폴백을 두지 않는다.** 설정 행·어댑터·키 중 하나라도 없으면 즉시 실패한다. 기본 모델로 조용히
넘어가면 관리 화면에서 바꾼 값이 실제로 쓰이는지 확인할 방법이 없고, 잘못된 모델로 뼈대 하나를 전부
생성한 뒤에야 알게 된다. 같은 이유로 **어댑터가 없는 벤더는 저장 시점에 거절**한다.

**API 키를 평문으로 두지 않는다.** DB 백업·덤프·읽기 권한이 곧 키 유출이 되고, 유출을 알아챌 방법도
없다. 마스터 키만 환경변수에서 온다 — 암호문과 키가 같은 DB 에 있으면 암호화가 의미를 잃는다.

### P1.4 주제 임베딩 (pgvector) ✅

- [x] 주제 임베딩을 **PostgreSQL pgvector**에 저장 (`V4__topic_embeddings.sql`)
- [x] 유사도 검색 — 코사인 거리 `<=>`, 컷오프 적용, 계층 이름 동반
- [x] **재임베딩 배치 경로** — 현황 조회 + 배치 단위 반복 실행
- [x] 저장 행에 **모델을 함께** 남기고, 검색이 현재 모델로만 비교

> 재임베딩을 나중으로 미루면 안 된다. 모델을 관리 화면에서 교체할 수 있게 만든 순간 재임베딩은
> *언젠가 필요한 것*이 아니라 *반드시 일어나는 것*이 된다. 경로가 없으면 교체 기능이 거짓말이 된다.

**`vector` 컬럼에 차원을 지정하지 않았다.** 모델을 화면에서 교체할 수 있는 이상 차원은 고정값이
아니고, 차원을 박으면 모델 교체가 마이그레이션을 요구해 그 결정과 정면으로 부딪힌다. 대가는 벡터
인덱스(HNSW·IVFFlat)를 만들 수 없다는 점이다 — pgvector 인덱스는 차원이 확정된 컬럼만 받는다.
감수하는 이유는 주제 수가 카탈로그 크기에 묶여 있어서다(초기 30~50개, 성장해도 수천). 반대로 챕터
임베딩은 뼈대마다 수십 개씩 늘어나 인덱스가 필수고, 그래서 Neo4j 쪽에 있다.

**모델 교체는 별도 무효화 작업이 없다.** 검색이 `model = 현재 모델`로 걸러 조회하므로, 모델을 바꾸면
기존 행이 전부 자동으로 대상에서 빠진다. 재임베딩이 끝나지 않은 주제는 **안 보이는** 쪽으로
실패한다 — 조용히 틀린 결과보다 낫다. 그리고 그것이 재임베딩 경로가 반드시 있어야 하는 이유다.

**임베딩만 JPA가 아니라 `JdbcTemplate`이다.** Hibernate의 벡터 매핑은 차원이 고정된 컬럼을
전제하므로, 엔티티로 매핑하려면 차원을 박아야 한다.

**신규·수정 주제를 즉시 임베딩하지 않는다.** 카탈로그 CRUD가 AI 키 설정 여부에 종속되면 안 된다.
벡터가 없는 주제는 그대로 재임베딩 대상이 되고, 사용자 매핑 경로(P1.5)는 신규 주제를 등록한 직후
명시적으로 임베딩한다 — 그 경로는 이미 AI를 쓰고 있다.

**모델 교체 시 배치가 자동으로 도는 것은 M2**다. 요청 스레드에서 전량을 돌리면 수천 건의 외부
호출이 한 요청에 묶인다. Kafka가 들어오면 설정 변경 이벤트가 배치를 트리거한다.

### P1.5 입력 → 뼈대 매핑

- [ ] LLM이 `도메인 → 분야 → 주제` 순으로 단계적 매핑
- [ ] 각 단계 후보를 수십 개 이내로 유지 (층별 좁히기)
- [ ] 매칭 시 기존 뼈대에 합류
- [ ] 미매칭 시 **유사 주제 후보 제시 → 사용자 확인** → 전부 거절 시에만 신규 주제 등록

사용자를 통합의 마지막 판정자로 세운다. 자동 생성으로 흘리면 오매칭 방지망이 없고, 운영자 승인
대기열로 보내면 사용자가 그 자리에서 학습을 시작할 수 없다.

## 여기서 정한 것

확정된 결정은 `CLAUDE.md`로 옮겼다. 아래는 그 요약이다.

| 항목 | 결정 |
|------|------|
| 스키마 관리 | Flyway 마이그레이션이 원천, `ddl-auto=none`. 제약은 DB에 둔다 |
| slug 유일성 | 주제는 전역, 분야는 도메인 내, 도메인은 전역. slug는 생성 후 불변 |
| 주제 수렴 1차 경로 | 별칭 테이블 + NFKC 정규화. 정규화 값은 전역 유일 |
| 인증 경로 분리 | 필터 체인 2개. 관리자 체인만 CSRF 끔(무상태 Bearer) |
| 최초 관리자 | 계정 0개일 때만 설정값으로 생성. JWT 서명키 기본값 없음 |
| AI 단계 | 4단계 + **임베딩** 5단계. 단계마다 벤더·모델 독립 설정 |
| AI 기본값 | 마이그레이션이 심는 행. 완성 4단계는 `claude-opus-5`, 임베딩은 Voyage `voyage-3-large` |
| API 키 저장 | AES-GCM 암호문. 마스터 키만 환경변수 |
| 폴백 정책 | 없음. 설정·어댑터·키가 없으면 즉시 실패하고, 미지원 벤더는 저장 시점에 거절 |
| 주제 임베딩 저장 | pgvector, **차원 미지정 `vector`**. 인덱스 없이 순차 스캔 (주제 수가 카탈로그에 묶여 있다) |
| 모델 교체 무효화 | 별도 작업 없음. 검색이 `model = 현재 모델`로 걸러 자동으로 배제된다 |
| 유사도 컷오프 | 초기값 0.55 (상수). 실측 후 설정값으로 뺀다 |
