# 문서

NEXT CHAPTER의 **구현 계획과 진행 상태**를 관리하는 곳이다.

> **결정의 원천은 `CLAUDE.md`다.** 제품 방향(Project Overview)과 설계(Architecture)는 거기에
> 있고, 이 폴더는 그 결정을 **언제·어떤 순서로 구현할 것인가**만 다룬다. 같은 내용을 두 곳에
> 적지 않는다 — 충돌하면 `CLAUDE.md`가 이긴다.

## 구조

```
docs/
  README.md                    ← 이 파일. 인덱스 + 진행 대시보드
  roadmap/
    README.md                  ← 로드맵 전체: 마일스톤, 의존 관계, 크리티컬 패스
    m0-foundation.md           ← 기반 골격과 CI
    m1-catalog.md              ← 카탈로그와 주제 매핑
    m2-generation.md           ← 뼈대 생성 파이프라인
    m3-consumption.md          ← 학습 경험 (웹)
    m4-personal-loop.md        ← 개인 루프
    m5-collective-loop.md      ← 집단 루프  ★ 3개월 필수 기준
    m6-delivery-formats.md     ← 딜리버리 확장 (영상·PPT)
    m7-operations.md           ← 운영 성숙
```

**마일스톤 하나가 파일 하나다.** 목표·완료 기준·페이즈·미결정 항목을 한 문서에 담아 상태를 한
화면에서 본다. 문서를 더 쪼개지 않는 이유가 그것이고, 반대로 마일스톤마다 폴더를 두지 않는
이유는 파일 하나짜리 폴더가 경로만 길게 만들기 때문이다.

## 상태 표기

| 표기 | 뜻 |
|------|-----|
| ⬜ 예정 | 시작하지 않음 |
| 🟡 진행 중 | 페이즈 하나 이상이 진행 중 |
| ✅ 완료 | 완료 기준(DoD)을 전부 충족 |
| ⏸ 보류 | 의도적으로 멈춤. 사유를 해당 문서에 적는다 |

페이즈 칸의 `0 / 6`은 **완료된 페이즈 수 / 전체 페이즈 수**다.

## 갱신 규칙

문서가 썩지 않게 하는 최소한의 규칙이다.

1. **페이즈를 끝내면 그 커밋 안에서** 마일스톤 문서의 체크박스와 이 대시보드를 함께 고친다.
   나중에 몰아서 하면 어느 시점의 상태인지 알 수 없게 된다.
2. **결정이 확정되면 `CLAUDE.md`로 옮긴다.** 마일스톤 문서의 "여기서 정해야 할 것"은 대기열이지
   보관소가 아니다. 확정된 결정이 로드맵에만 남아 있으면 설계 문서가 거짓이 된다.
3. **범위가 바뀌면 페이즈를 지우지 말고 상태를 바꾼다.** 왜 안 했는지가 남아야 한다.
4. 로드맵 문서는 **완료 기준(DoD)까지만** 적는다. 구현 방법은 코드와 `CLAUDE.md`에 있다.
